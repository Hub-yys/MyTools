# 鸣潮工具箱（WutheringWavesTools）

一个 Python + Qt 的桌面工具箱。左边侧栏「主页 / 工具」，**主页平铺所有工具（不分类）**，
点一下卡片直接跳到那个工具。

> ⚠ **改名说明（2026-09-24）**：产品名从 `MyTools` 改为 **WutheringWavesTools / 鸣潮工具箱**，
> exe、安装包、安装目录、用户数据目录都换了名字。**旧的 `%LOCALAPPDATA%\MyTools` 会在首次
> 启动时整树继承到 `%LOCALAPPDATA%\WutheringWavesTools`**（复制而非移动，老目录留着兜底；
> 见 `src/core/paths.py::migrate_legacy_user_data`）。源码目录与仓库名仍是 `MyTools`。

界面用 PySide6 + [PySide6-Fluent-Widgets](https://github.com/zhiyiYo/PyQt-Fluent-Widgets)，
工具组织方式参考了 [ok-ww](https://github.com/ok-oldking/ok-wuthering-waves) 的「注册表 + 自动发现」思路：
**加一个工具 = 加一个文件**，不用在任何地方手动登记。

## 跑起来

> ⚠ **必须用「管理员」终端跑**（2026-09-30 起）。不是管理员时程序会弹框提示
> 并以非 0 退出 —— 因为游戏在高完整性级别运行，普通权限下所有游戏功能都点不动。
> 直接用普通 PowerShell 跑会**起不来**，这不是 bug。

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt --no-deps
.venv\Scripts\python main.py
```

`--no-deps` 不是可选项：`PySide6-Fluent-Widgets` 的元数据声明依赖**完整版 PySide6（245MB）**，
但它运行时只用到 QtWidgets / QtGui / QtCore / QtSvg / QtNetwork，全在 **PySide6-Essentials（77MB）** 里。
依赖已在 `requirements.txt` 里全部显式列出，跳过解析就不会去拉那个大包。

> 只想**看界面/跑测试**（不碰游戏功能）时，不需要管理员：
> `tests/` 里的单测和冒烟脚本都直接跑，不受启动闸门影响
> （闸门只在 `main()` 里，测试不进那条路）。

### PyCharm

用 File → Open 打开项目目录即可。`.idea/runConfigurations/MyTools.xml` 里已经放好
**MyTools** 和 **Smoke Core** 两个运行项；解释器指向 `.venv\Scripts\python.exe`。
如果 PyCharm 没自动认出 `.venv`，手动在 Settings → Python Interpreter 里指过去。

> ⚠ 因为启动要求管理员，**PyCharm 本身也要以管理员身份运行**，
> 它拉起来的 `main.py` 才带管理员权限（子进程继承父进程的权限）。

### 离线安装（网络慢的时候）

单连接 pip 在某些网络下只有 18KB/s，装 77MB 要一个小时。`tools/fetch_wheels.py` 用
16 连接分段下载 + 断点续传，实测 **313 KB/s**（快 17 倍），中途断了重跑即可接着下：

```powershell
.venv\Scripts\python tools\fetch_wheels.py          # 下载到 wheels/
.venv\Scripts\python -m pip install --no-index --find-links wheels --no-deps `
    PySide6-Essentials shiboken6 PySideSix-Frameless-Window darkdetect pywin32 PySide6-Fluent-Widgets pypinyin
```

## 配置

侧栏「配置」页，目前有**三类**配置（点「新增」时先选类型）：

| 类型 | 一条 = 什么 | 数据 |
|---|---|---|
| **角色声骸筛选** | 一个角色 + 一套套装 + 4C/3C/1C 各一个声骸 | `data/loadouts.json` |
| **角色声骸强化** | 一套强化判定条件（核心属性 / 双爆下限 / 有效词条数…） | `echo_profiles.json` |
| **角色战斗**（2026-09-30 新增） | 一个角色的技能快捷键 / 链路 / 战斗脚本 | `battle_profiles.json` |

三类都是**一个角色一条**（用户 2026-09-26 要求），角色只能从下拉里选、不能自由输入。

### 角色战斗配置

用户 2026-09-30 要求新增，字段：

| 字段 | 说明 |
|---|---|
| 角色 | 下拉选择（已被别的配置占用的选不到） |
| 角色头像 | **与角色联动** —— 下拉选谁就显示谁的头像 |
| 技能快捷键 | 声骸技能 **Q** / 共鸣技能 **E** / 共鸣解放 **R**（默认值，可改） |
| 角色链路 | `[−] N [+]`，**范围 0~6**，到边界按钮灰掉 |
| 角色战斗脚本 | 多行文本框 |

> ★ **现在只存不跑**（用户明确："先只存不跑"）——
> 快捷键和脚本都只是存下来，界面能编辑 / 保存 / 回填，
> **没有接任何按键执行**。以后要做执行时，从这里读、显式注入任务即可。
>
> ⚠ **别去和工具页的设置联动** —— 另两类配置立的规矩就是"配置只是存着，
> 不改变工具自己的设置"（用户 2026-09-26 否掉了"配置即工具规则"那套设计）。

几个实现约定：

- **链路夹取只有一份**（`battle_profile.clamp_chain`）—— 界面的 +/− 和加载时
  都调它，否则会出现"按钮夹了、读盘没夹"的越界值；
- **快捷键统一存大写**（`q` → `Q`）：同一个键不该看着像两个；
  空格子**回落到默认值**（存空串会让界面那一格空着，像坏了）；
- **稳定 id**：和另两类一样有 `id`，老数据缺 id 时补发并**立刻落盘**
  （不落盘的话每次启动换一个新 id，任务里指向它的步骤就永远找不到）。

### 数据从哪来

角色名单和套装资料放在 `src/core/data/` 下的三个 JSON 里，都带
`_source` / `_fetched` 字段，注明**整理自哪里、什么时候抓的**：

- `wuwa_characters.json` —— 58 个角色：名字 + 稀有度 / 属性 / 武器
- `wuwa_echo_sets.json` —— 34 套套装：名称 + 2/5 件套效果原文 + **每套有哪些声骸**
- `wuwa_set_versions.json` —— 34 套各自的**出场版本**（如 `3.5`）

**版本表是人工整理的**，因为它没法从 wiki 抓：wiki 那张套装表是按
`sort=名称` 排的，压根没有版本栏。所以照库洛官方各版本「内容说明 / 更新预告」
里的『新增【合鸣套装】』逐条核对，再和巴哈姆特《声骸套装&图鉴》的版本分组交叉验证。
**界面按版本倒序排**（最新的在最前面）—— 资源库列表和配置页下拉都走这个顺序。

更新：跑 `python tools/refresh_wuwa_data.py`（刷效果 / 声骸明细，**不会动版本表**），
或直接改那几个 JSON。

**图标不随代码走**（它们是游戏美术素材）—— 用
`python tools/fetch_wuwa_assets.py` 从公开 wiki 拉到本地：角色头像 58 +
套装图标 34 + 声骸图标 125 = **217 张**。详见下面「资源库」一节。

### 新增 / 修改表单

| 项 | 说明 |
|---|---|
| 角色 * | **点输入框就摊开候选**（当前选中的名字不会被清掉），一打字就切回过滤；**中文、全拼、首字母都能搜**（`爱弥斯` / `aimisi` / `ams` 都行，一条都不匹配就收起，不留空框）。**已经被别的配置占用的角色不在候选里**（一角色一条），保存时还会再校一次 —— 所以**不能**随手输一个不存在的角色（那样头像会空白，见下）。头像显示在角色下方，跟着角色自动联动 |
| 角色头像 | 头像框**默认空白**，选到角色会自动补上该角色的头像；点「更换」可以挑一张自己的图（之后不再跟角色联动 —— 再换角色会把自定义头像清掉，回归联动） |
| 声骸套装 * | 下拉里带**套装图标 + 名称**，列出**全部 34 套**，顺序为**出场版本倒序**（最新的在最前面）—— 和资源库那份完全一致。明细还没收录的套装也能选，只是对应档位会空着并提示（见下） |
| 4C / 3C / 1C * | 只列该套装对应档位的声骸。一行 = 图标+名称（左）／属性（中，**每行单选**：勾第二个会自动取消第一个）／勾选该声骸（右）。**同一档位可以勾多个声骸**，每个声骸各带一条属性 |

**每档的候选属性 = 该档真实的主词条池**（在 `src/core/game_data.py` 的 `STATS_BY_COST`）：

| 档位 | 主词条池 |
|---|---|
| 4C | 暴击 / 暴击伤害 / 治疗加成 / 攻击百分比 / 防御百分比 / 生命百分比（6 条）|
| 3C | 攻击百分比 / 防御百分比 / 生命百分比 / 共鸣效率 / **六种属性伤害加成**（冷凝·热熔·气动·导电·衍射·湮灭，共 10 条）|
| 1C | 攻击百分比 / 防御百分比 / 生命百分比（**只有百分比，没有固定值**，3 条）|

三档的"固定攻击 / 固定生命"是声骸**自带的固定词条**，不是可刷的主词条，所以都不列。
属性框按**固定 5 列**排布，超出自动换行（3C 10 条会占两行）。

> 老配置里若存着已不在池里的属性（比如 3C 早先那个笼统的「属性伤害加成」），
> 打开「修改」时会**把那条单独列出来并勾上**，而不是默默丢掉 —— 改选具体属性即可。

必填项没填时点「保存」**不会关窗**，会弹提示说明缺什么。**只有角色和声骸套装是必填** ——
**1C / 3C / 4C 都可以不填**（2026-09-28 用户要求：不校验必填）。套装没选时只提示"请先选择声骸套装"。
已经选了声骸却没选属性的，仍会提示补属性（半截数据筛选步骤生成不出来）。

「状态」默认勾 **已锁定**（2026-09-28 用户批注"默认已锁定"）；「品质」默认只勾五星。

### 列表

每条一行：左边**头像 + 角色名（名字在头像下面）**，中间**摘要居中显示、超长自动换行**，
右侧 **查看 / 修改 / 删除**。「查看」是只读详情；「删除」有二次确认。

> ⚠ **被任务流程引用的配置不能删**（2026-09-28 用户要求："已完成任务流程里使用的配置，
> 不能直接删除配置，需要先删除任务，才能删除配置"）。
> 点删除会弹框告诉你**是哪几条流程**在占用，让你先去「任务」页删流程。
>
> 为什么必须拦：配置步骤靠 `key` 指向配置，配置一删那一步就成了**悬空引用** ——
> 界面上显示成「xxx（配置已不在）」，运行时工具拿不到配置，**等于那一步静默失效**，
> 用户看到的是"流程明明还在，却不筛选了"。
>
> 判定在 `core/tasks.py` 的 `flows_using_config()`（纯逻辑、可单测），
> 配置页两个删除入口都调它。匹配时 **id 和名字一起比** —— 2026-09-26 之前
> 强化配置还没有 id，老流程步骤里存的是角色名（见 `config_names.find_config`），
> 只比 id 会漏掉这类引用。

> 角色名走 **单行 + 超宽省略号**（悬停出 tooltip 显示全名）。
> 以前是个既没限宽、也没开换行的标签，长名会横向溢出把摘要挤变形 ——
> 2026-09-26 和「角色声骸强化」那行一起修的（见 `compat.ElidedLabel`）。

行高跟着摘要行数走（窗口宽度变了会重算）。实现上要注意：QLabel 自动换行的高度靠
`heightForWidth`，而 Qt 的 `QBoxLayout` **不传播**它 —— 所以摘要的宽度是先算好再定死的，
见 `config_interface.py` 的 `LoadoutRow.set_summary_width()`。

存储格式：每个档位的 `picks` 存的是**列表**（支持多选）；老版本存的单条对象也能正常读出来。

  组内按星级倒序、同星级按名字。

### ★★ 角色排序：按「实装版本」降序（我改错了两次）

用户 2026-10-24 两次指出问题：

> ① 资源库最新的角色图标为什么没排到前面

> ② 什么情况，这个排序完全有问题，排序按照版本推出的新角色降序排列，
> **注意是新角色，不算复刻的角色**

#### 两个错误依据（都别用）

| 我试过的 | 为什么错 |
|---|---|
| **数组原顺序** | 数据是"手工补的排最前 + 官方新角色 append 到末尾"堆出来的 → 新角色反而垫底 |
| **`content.updateAt`** | 那是**词条最后修改时间**！wiki 批量改数据时全刷新 → 老角色也"变新" |

第 2 个错的后果（用户截图）：

```
锁暝 琳奈 洛瑟菈 尤诺 千咲 心 莉莉 赞妮
                  ↑ 千咲(V2.8) 夹在 V3.x 中间
莫宁 绯雪 景燃 清宵 达妮娅 吟霖 忌炎 爱弥斯
                        ↑ 吟霖/忌炎(V1.0) 跑到 V3.5 前面
```

#### 正确依据：库街区的「实装版本」标签

catalogue 1105 的 tagTree 里有 **「实装版本」** 分组，值形如 `V3.8` / `V3.7` / … / `V1.0`。

**为什么它正好符合要求**：

* 按版本号大小排 = "版本推出的新角色在前"
* **复刻不改变实装版本** → 天然排除复刻 ✅（用户特别强调这点）

> ⚠ 代码里原本有一行注释写着「实装版本 / 风格定位：本地用不上」——
> **那是错的**，正是漏掉正确依据的原因。已改。

#### 两个实现细节

1. **版本号必须按数字比，不能按字符串**
   —— 否则 `V3.10` 会排在 `V3.9` 前面（下个版本就会踩到）。
   做法：`CharacterInfo.version_key` 解析成 `(major, minor)` 元组。

2. **复刻的干扰已经天然排除**，不用额外判断。
   如果哪天需要区分"首发 vs 复刻"，再看别的字段。

现在的顺序（2026-10-24 实测）：

```

V3.7 心 锁暝
V3.6 景燃 清宵
V3.5 漂泊者·导电 秧秧·玄翎 穗穗
V3.4 丽贝卡 洛瑟菈 露西
…
V1.1 今汐(42) 长离(43)
V1.0 吟霖 忌炎 卡卡罗 白芷(58)
```

`tests/test_character_ordering.py` 用 14 条测试守着，其中：

* `test_numeric_not_string_order` —— 钉住 `V3.10 > V3.9`
* `test_does_not_use_updateat` —— 就算数据里有 `released_at` 也不许影响排序
* `test_no_stale_released_at` —— 数据文件里不该再有那个错字段
* `test_user_cited_characters_are_in_right_places` —— 用户点名的
  `千咲`/`今汐`/`长离` 位置要对

### 资料从哪来

页面不写死任何一条资料，全部读 `src/core/data/*.json`。**资料整理自公开 wiki**
（库街区官方 wiki），页面上会写明「抓取于 X（游戏版本 Y）」——
**这是第三方 wiki 的数据，游戏更新后可能过期**。

### 怎么更新

```powershell
.venv\Scripts\python tools\refresh_wuwa_data.py            # 只刷套装效果（快，1 个页面）
.venv\Scripts\python tools\refresh_wuwa_data.py --echoes   # 顺带刷声骸明细（34 个页面）
.venv\Scripts\python tools\refresh_wuwa_data.py --all --write
```

默认只预览，加 `--write` 才写盘。按套装名 merge，不会动其它字段。

**「资源库更新」工具会自动同步四类数据**（见 `core/wuwa_update.py`）：

| 数据 | 来源 | 说明 |
|---|---|---|
| 套装名单 + 效果原文 | **库街区** 1219 | 效果走 `getEntryDetail` 详情 |
| 声骸掉落池 + 技能说明 | **库街区** 1107 | 技能同上；只增不减 |
| **角色名单** | **库街区** 1105 | **新角色追加 → 配置页立刻能选到** |
| 角色 / 武器图标 | **库街区** 1105 / 1106 | 抽卡卡片墙用 |

#### ★ 「获取最新数据」会自动补图（2026-09-30 新增）

用户报："资源库已经更新了，这图片为什么没自动补上？"

`tools/fetch_wuwa_assets.py` 那个手动脚本干的。于是"数据更新了、图还是空的"。
**这两件事本就不该分开。**

现在 `apply_updates()` 最后会调 `_download_missing_icons()`：

- 用 `icon_urls` 里的 URL 逐个补下（`core/assets.py`）
- ⚠ **只补缺、绝不覆盖** —— 用户可能自己换过图（README 就教了"覆盖同名文件"），

#### ★ 声骸技能：别"每次都重拉一遍"（2026-10-01 修）

用户报："这里为什么老是要拉取，我本地本来就是最新的"。

根因：判断"要不要拉"的条件是**有没有 skill 正文** ——
但有些声骸（活动 / 装饰类）库街区详情里**根本没有「声骸技能」模块**，
它们永远不会有正文，于是**每次更新都白拉一遍**（那十几个 + 每个 0.35s 间隔）。

下次直接跳过（库街区和 bwiki 两条路都跳过）。
报告里会写"确认 N 个声骸没有技能说明（记下来，以后不再重复拉取）"。

> ⚠ 两条保命规则：
> 1. **绝不能用"没查到"覆盖已有的正文** —— 那是数据倒退；
> 2. 后来真补到正文了，标记要**作废**（否则数据和界面自相矛盾）。

#### ★ 「效果更新 N 套」的假报（2026-10-01 修）

用户报："本来就有 你这是更新什么" —— 明明数据没问题，每次检查都说
**「效果更新 30 套」**。

根因：本地效果**是从库街区写入的**（2026-09-30 改成库街区优先），
但 `check_updates()` 里**只拿 bwiki 那份去比**。两个源的文字**本来就有出入**：

| 来源 | 5 件套文字 |

| bwiki | （同上）`延奏技能伤害提升60%` ← **多一句** |

### 声骸明细（数据来源与已知缺口）

数据来自**声骸自己的 wiki 页面**：每页都写了 `所属套装`（英文逗号分隔）和 `COST花费`。
这个 wiki 开了 SemanticMediaWiki，所以用 `action=ask` **一次就能把 139 条声骸全查下来**，
再反过来拼出「套装 → 声骸」。同一条声骸经常属于多个套装（例如「重工铁蹄」同时属于
逆光跃彩之约 / 雪落无声之愿 / 剪心辑梦之影），所以必须走反向索引，不能只看套装详情页。

> ⚠ 早期版本是抓 `声骸合鸣/<套装名>` 详情页的，**那样会漏**——详情页上是编辑手工挑的一小撮。

**但即便如此，wiki 本身仍有缺口**，这不是程序问题：

| 版本 | 情况 |
|---|---|
| 1.0 / 2.0 | ✅ 完整（编辑填过完整的掉落池）|
| 2.2 ~ 2.8 | ⚠️ 只登记了「该版本新增的专属声骸」，3C/1C 基本为空 |
| 3.0 ~ 3.3 | ⚠️ 4C/3C 有，**1C 为空** |
| 3.4 | 1 件套联动套，只有一个 4C（**本来就该只有一个**）|
| 3.5 | ✅ 完整 |

根因：`所属套装` 这个字段只被认真填过老套装和当版本新增的小怪；

想补齐只有两条路：等 bwiki 更新后重跑 `refresh_wuwa_data.py --echoes`，
或者你知道某套的 1C 是哪些，直接写进 `wuwa_echo_sets.json` 对应那一套的 `echoes` 数组。

不会拿 3C/1C 来卡你（`EchoSetInfo.required_costs` 会按件套数算）。

> 资源库的套装卡片**只显示套装名 + 2/5 件套效果**，不再列声骸条数统计。

## 声骸自动强化

**流程整段用 ok-ww 的 [`EnhanceEchoTask`](https://github.com/ok-oldking/ok-wuthering-waves)**，
MyTools 只提供两样东西：界面上的筛选条件，以及"把条件注入任务再启动"的接线
（实现在 `src/tools/game/echo_enhance/okww_task.py`）。

强化动作全在 ok-ww 那边：点「培养」进强化界面 → 「阶段放入」→「强化并调谐」→
关掉「调谐成功 / 不再提示」弹窗 → OCR 读词条 → 判定 → 按 `Z` 弃置或按 `C` 上锁，
直到列表里没有 0 级声骸。

> ⚠ 2026-09-23 改版：原来 MyTools 自己写了一套点击/OCR（`controller.py` / `runner.py` /
> `reader.py`），**在别的机器上完全没用**。而同期的「4C 自动战斗」走 ok-ww 引擎是通的 ——
> 同一件事有两套实现，那就只留跑得通的那套：流程搬 ok-ww 的，判定条件用界面上的。
> 旧的四个模块保留着（还有测试覆盖），但已不是主路径，文件顶部有 LEGACY 标记。

### 两个曾经让它「完全没用」的坑（2026-09-24 已修）

两个都是**静默失败** —— 页面一切正常、点「运行」却什么都不发生，值得单独记一笔：

1. **任务被 ok-script 静默跳过。** ok-ww 的 `EnhanceEchoTask` 声明了
   `supported_languages = ["zh_CN", "zh_TW"]`，而 ok-script 的 `init_tasks()` **不满足
   就直接不注册**；宿主没有 GUI，`app.locale` 实测是 `en_US` —— 于是任务根本没进引擎，
   点「运行」只会得到「找不到任务」。子类里清空 `supported_languages` 即可。
   现在 `tests/check_okww_registration.py` 会真起一次引擎把 `TASKS` 数一遍，
   这类"静默消失"不会再无声发生。
2. **判定规则自相矛盾。** 有效词条集合只有双爆（2 条）而界面要求 ≥3，而声骸每种
   词条最多出现一次 → 永远达不到 → **每个声骸都在满级那一刻被弃置**。

现在「有效词条数」与核心/可选属性**联动**（`settings.valid_count_range()`）：

* **不可小于核心属性条数** —— 核心属性是"必须有"，全都到齐就天然有那么多条有效词条；
* **不可大于有效词条集合的总条数** —— 每种词条只会出现一次，集合里没有的种类凑不出来。

加减框直接停在合法范围里，卡片下方有一行实时提示。所以默认只勾双爆时它只能是 **2** 条；
想要求 3 条以上，先在「可选属性」里多勾几条。

**改核心属性时这个数会跟着回到核心属性条数**（减少核心也会跟着降），之后仍可往上调 ——
不然"核心从 3 条改成 2 条、有效词条却还停在 3"会让人以为联动没生效。

运行结束时信息栏会给出**弃置原因分布**（「双爆不达标 N、有效词条不足 M」）——
规则太严、还是词条读错了，一眼就能分清。

### ★ 3.7 声骸堆叠导致"强化完就停"的修正（2026-10-02）

用户报："3.7 更新后，更新了声骸堆叠，导致强化好了一个声骸后，会自动跳到
强化好的声骸位置，从而不能继续强化到其他声骸了"。

**根因**（读 ok-ww 的 `EnhanceEchoTask.run()`）：它的循环**从不主动选下一个**，
而是假设"强化完 ESC 回列表，光标还在原位"：

```python
while True:
    enhance = self.find_echo_enhance()   # 右边"培养"按钮在不在
    current_level = self.is_0_level()    # 当前声骸是不是 0 级
    if not current_level:
        return                            # ← 认为干完了，收工
    self.click(enhance)                   # 强化**当前光标**那个
```

**堆叠打破了"光标还在原位"这个假设** —— 强化好的被归类重排、光标被带过去
→ `is_0_level()` 读到"不是 0 级" → **直接收工**。
**所以不是"不能强化"，是它以为干完了。**

**修法**：用户实测确认「滚动不能移动光标，上下左右也不能，**只能鼠标点击**」
→ 在两个收尾动作（`lock_and_esc` / `trash_and_esc`）之后，
**扫一遍网格、点第一个未强化的**。

改动在 MyTools 自己的 `MyToolsEnhanceEchoTask` + 新模块
`echo_enhance/echo_grid.py` —— **不碰 `vendor/`**。

#### 判据：卡片左下的**层叠图标**

卡片底部只有两种形态：

| 卡片底部 | 含义 |
|---|---|
| **层叠图标 + 数字** | **持有数量** → 未强化 |
| **只有 `+N`** | **强化等级** → 已强化 |

实测（两张实机截图 × 全部格子，走 ok-ww 的 `find_one` 路径）：

| 未强化（有图标） | 已强化（无图标） |
|---|---|
| **0.887 ~ 1.000** | **0.047 ~ 0.085** |

完全不重叠 —— 比 OCR 判 `+N` 可靠得多（那个小字带斜纹底，容易读错）。

#### ⚠⚠ 一个必需但反直觉的细节：搜索框必须**大于**模板

| 配置 | 漏检格数 | 未强化最低分 |
|---|---|---|
| 放大模板 + pad 0 | **7 格** | 0.321 |
| 原尺寸 + pad 0 | **7 格** | 0.321 |
| 原尺寸 + **pad 6** | **0 格** | **0.887** |

`cv2.matchTemplate` 在"搜索图尺寸 == 模板尺寸"时**只产出一个值**，
没有滑动余地 —— 每张卡 1~2 像素的位置偏差就让得分从 1.00 掉到 0.36。
`SEARCH_PAD = 6` **不是保险，是必需**。

> ⚠ 模板**必须按裁剪时的分辨率存**（1280×720），**不要放大**到游戏设置里的
> 分辨率 —— 放大再缩小 = 细节全丢（实测 0.36）。
> 生成脚本：`tools/make_echo_stack_template.py`

### 列表搜索（2026-09-30 新增）

用户要求："加上搜索，和前面下拉列表搜索一样的"。

配置页顶部有搜索框，规则**和下拉框完全一致**（中文子串 + 拼音全拼/首字母）。
做到"一致"的办法不是抄一遍，而是**共用一份实现**：

```python
# gui/pickers.py —— 全项目唯一的匹配规则
def matches_keyword(keys, text, keyword) -> bool: ...
```

下拉框的 `FilterComboBox._matches()` 和配置页的搜索框都调它。
`tests/test_config_search.py` 直接从源码里查这条接线 ——

几个细节：

- 搜索时副标题变成 **`命中 2 / 共 11 条`** —— 带上总数，
  否则用户看到"共 1 条"会以为配置被删了；
- 搜不到时的提示**带上搜索词**（"没有匹配「zzz」的配置"）——
  和"还没建过配置"是两回事，混在一起会让用户白找；
- 过滤**只影响显示、不动存储**：行还是照常从存储读出来，只是不命中的不摆上来；
- `matches_keyword` **自己 strip** —— 调用方忘了去空格时，
  `"   "` 会被当成关键词，结果一条都搜不到（看起来像"搜索坏了"）。
- 名字必须**精确命中**一个角色，否则保存时会被拦下 —— 这条不是洁癖：

- **一个角色只能有一条配置**：已被占用的角色**不在候选里**，保存时再校一次

  > （早先定的规则），它不显示存盘值 —— 所以"跟工具页一样"＝出厂默认。

### 判定顺序（每调谐出一批词条就跑一次）

按下面顺序逐条查，任一条命中就**直接弃置**，都不命中才是继续强化 / 上锁：

| 顺序 | 规则 | 触发条件 |
|---|---|---|
| 1 | 核心属性凑不齐 | `缺失的核心条数 > 剩余孔位` —— 剩下几个孔已经不够把缺的核心补出来了 |
| 2 | 双爆不达标 | 暴击、爆伤**都出现后**，任一项低于各自下限（右侧开关可整体关掉） |
| 3 | 有效词条数不够 | `当前有效条数 + 剩余孔位 < 要求的条数` |
| 4 | 上锁 | 上面都通过、且已出满 5 条 → 按 C 保留 |

第 1 条**不是**"缺核心就弃置"。逐级强化时刚进界面一条词条都没出，那时永远是"缺全部核心"，
一刀切弃置会导致一件都强化不了。它的真实语义是 **"剩下几个孔 < 还缺几个核心"才弃置**；
缺核心但孔位还够，就继续调谐去博（这跟"最终不留缺核心的声骸"是等价的，只是弃得更早、更省时间）。

**触发时机跟核心勾了几条直接相关**：默认核心只有双爆 2 条，所以第 1 条规则实际要到
**已出 4 条词条（剩 1 孔）**才会生效；已出 3 条、一条核心都没有时，是第 3 条（有效词条数）先拦下来。
如果核心勾到 4~5 条，这条规则会明显提前触发。

### 定时关机（2026-10-01 新增）

运行卡下面是**定时关机**卡：勾「启用」+ 填分钟数（1 ~ 1440），
点「启动」开始计时，到点自动关机。关机前 **60 秒弹提醒，可取消**
（用户明确要求"提前提醒且可取消"）。

| 行为 | 说明 |
|---|---|
| 计时起点 | **点「启动」那一刻**（"跑 N 分钟后关"），不是固定时刻 |
| 关机前 | 弹窗提醒，**可取消**（取消后本次不再自动关） |
| 点「停止」 | **一并取消定时关机** —— 否则你以为停了就没事，到点电脑还是关了 |

纯逻辑在 `src/core/shutdown_timer.py`：

- `ShutdownTimer` 是**纯状态机**（不碰 Qt、不真关机），
  `should_warn()` / `should_fire()` 各**只报一次**（轮询每 300ms 一次，
  不"只报一次"会连着弹几十个框）；

- `shutdown()` 命令失败会**如实返回失败** —— 绝不"假装关了"
  （用户以为会关、结果没关，比直接报错糟得多）。

> 测试里**绝不真的关机**：状态机喂时间戳即可；
> `shutdown()` 只验证它构造的命令对不对（把 `subprocess.run` mock 掉）。

### 战斗报告（2026-09-24 新增）

运行卡下面是一张**战斗报告**卡，跟着 300ms 轮询边跑边刷新，显示五项：

| 项 | 内容 | 数据来源 |
|---|---|---|
| 使用队伍 | 圆形头像 + 角色名 | `task.chars`（ok-ww 的屏幕模板匹配）；英文类名经它的 `i18n/zh_CN` 转中文，再对上 MyTools 的角色数据与头像 |

> ★ > ★ **「锁定声骸」为什么要挂钩子**：ok-ww 完全不区分拾取到的声骸是锁了还是弃了
> （`incr_drop()` 只把 `info['Echo Count']` 加一）。所以 4C 刷声骸改用一个小**子类**
> （`auto_combat/okww_farm.py`，刷取流程照旧），在拾取动作后读一次左下角的角标 ——
> 用的是 ok-ww 自带的特征 `echo_locked` / `echo_not_locked` / `echo_dropped` /
> `echo_not_dropped`（跟它强化界面判锁/弃置是同一套图标）。
> 报告底部还会列出 **锁定 / 弃置 / 都没** 三个数：万一判定区域对不上，
> 会表现为「锁定、弃置恒为 0、都没 = 全部」，一眼就能看出来，不会被默默吞掉。

> **其余四项不是 MyTools 做的** —— ok-ww 自己一直在算，只是塞在任务的 `self.info` 里当
> "实时信息"显示（它**没有**报告界面）。本报告只是把这些数字"翻译"出来，所以不碰
> ok-ww 的执行逻辑。
> ⚠ 因为 `info` 在同一个进程里**跨次运行累加**，报告显示的是「当前 − 开跑前快照」的差值 ——
> 也就是你要的"本次 4C 自动战斗"。

### ★ 点「启动」立刻最小化（不是等任务真正起来）

用户 2026-10-24 报：

> 启动或运行后并没有最小化程序

**原来为什么不动**：只在 `MainWindow.task_started` 信号里最小化，
而那个信号是 OK 宿主在 **任务真正启动之后** 才发的。

问题在于**第一次点启动时引擎还没 boot** ——
`start_task` 只是把任务**排队**然后立刻返回，信号不会来。
而 boot 要几秒到几十秒（加载 OCR 模型），界面就一直不动，
用户自然会以为"点了没反应"。

**修法**：`_on_start` 末尾直接调 `_go_background_now()` →
`self.window().go_background_to_game()`，**不等任务真起来**。

好处：立刻有反馈、boot 期间本来也不用看界面、失败了点任务栏图标回来能看到错误。

> ⚠ 用 `self.window()` 拿主窗口，拿不到就静默跳过 ——
> 最小化是体验优化，不该影响启动本身。

### ★ 修的 ok-ww bug：守岸人永远不放重击

用户实测："ok-ww 的守岸人不释放重击"。查下来是**上游的一个 bug**：

```python
# ok-ww 原版 ShoreKeeper.do_perform
if not self.click_resonance():
    self.heavy_click_forte(self.is_mouse_forte_full)
```

`click_resonance()` 返回的是**元组** `(clicked, duration, has_animation)`
—— 元组**永远是真值**，所以 `not 元组` **永远是 False**，
那句重击是**死代码**。

**修法**：摘掉 `if not ...` 包装，改成无条件调用 ——
和 ok-ww 自己的 **Changli**（同样是"攒满→重击"型）写法一致：

```python
self.click_resonance()
self.heavy_click_forte(check_fun=self.is_mouse_forte_full)
```

`heavy_click_forte` 内部会先调 `check_fun()`（能量满没满），
没满就什么都不做 —— 所以**无条件调用是安全的**。

> ⚠ 这处改在 `vendor/` 里（上游更新会冲掉），靠
> **`tools/install_xin_patch.py`** 重放 —— 和「心」的支持同一套机制。
> 跑 `.venv/Scripts/python tools/install_xin_patch.py --apply` 装回。
>
> ⚠ 该脚本有**两种模式**：`_patch`（插在后面）和 `_patch_replace`（替换）。
> 守岸人这处必须用**替换** —— 第一版错用了插入，结果旧的 bug 代码还在、
> 新的只是被加在它后面（等于没修）。`tests/test_shorekeeper_heavy.py`
> 现在用 AST 盯着这点。

> ⚠ **2026-10-24 复查：上游仍未修这个 bug**，所以升级 ok-ww 之后
> **必须重放这个 patch**，否则「守岸人不放重击」会复发。

ok-ww 配置里还注册了触发式的 `AutoCombatTask`（进战斗自动输出），
当前页面未暴露入口。

## 声骸批量调频（改主属性）

**花材料把一批声骸的主属性统一改成指定属性**，走声骸详情页的「数据重构」。

> ⚠ 别和「声骸自动强化」混：**强化**改**副词条**（强化并调谐），
> **调频**改**主属性**（数据重构）。两件事。

流程来自 ok-ww 的 `ChangeEchoTask`，但**容错按本工具的标准重写**
（原版会在几种常见情况下把整个任务打断，见下）。设计说明在
`docs/声骸批量调频工具设计.md`。

### 前置条件

1. **以管理员运行**本程序（同上：鸣潮跑在管理员权限下，低权限发不出点击且不报错）；
2. 游戏用**窗口模式**；
3. 自己先走到：**背包(B) → 声骸 → 用过滤器筛出要调频的 → 按等级升序排序**，停在列表界面；
4. 过滤器**别把目标属性包含进来** —— 否则筛出的第一个就是目标属性，工具会停下来提醒你。

### 相对 ok-ww 原版改了什么

| 原版行为 | 这里 |
|---|---|
| `supported_languages = ["zh_CN"]` | **清空** —— 否则被 ok-script 静默不注册，任务"凭空消失"（和声骸强化踩过的同一个坑） |
| 选项表含 `攻击` / `生命` / `防御`（**副词条**形态） | 改成 `攻击百分比` / `生命百分比` / `防御百分比` —— 声骸**主属性**只有百分比形态，原版那三个在游戏里选不到 |
| 属性名用**子串**比较（`"攻击" in "攻击百分比"` = True） | 改成**精确相等**。原版会把"该改的"误判成"已经相同"并**直接抛异常中断任务** |
| 选项检索用字面量 `re.search(target, …)` | 改成**整串 + 允许「力/值」**的匹配式。字面量既漏「攻击**力**百分比」，又会把 `暴击` 撞到 `暴击伤害` 那个框上（**点错选项**） |
| 「目标属性和当前属性相同」→ `raise` | 记一次**跳过** → 停下并提示**收紧过滤条件**（ok-ww 的循环只会处理列表第一个声骸，"跳过继续"会死循环） |
| 五处 `raise_if_not_found=True` | **有限重试**（3×1s）；仍失败记成"这个声骸失败"、回列表、**继续下一个**；连续失败 3 个才整体停 |
| `esc()` 上限 5 秒 | 放宽到 10 秒，且**确认真的回到列表**（没回来会补按一次） |
| 只统计"成功" | **成功 / 跳过 / 失败**三个数分开（跳过 ≠ 失败） |

### 接线（★ 新增任务时最容易漏的一步）

一个工具页上的任务要真正跑起来，**两处都得改**，少一处就是"页面上一切正常、
点启动什么都不发生"：

1. `okww_boot.TASKS` —— 页面上的名字 → 任务类名；
2. `build_config()["onetime_tasks"]` —— 引擎的注册表，写 `[模块路径, 类名]`。

外加任务类自己的 `__init__` 里 **`self.supported_languages = []`**（宿主是 headless，
引擎语言是 `en_US`，不清空会被 ok-script **静默跳过**）。

> 2026-09-25 就是漏了第 2 步：`TASKS` 加了「声骸批量调频」、
> `onetime_tasks` 却还指着 vendored 的原版 `ChangeEchoTask`（而原版带语言门禁，
> 自己也被跳过），结果**两边都没注册**。全量单测当时全绿——
> 因为 `test_tasks_exposed_to_page` 只点名断言了另外两个任务。
> 现在它改成**遍历 `TASKS`**，新增任务时漏写注册表会立刻红，
> 不用等起引擎（`check_okww_registration.py`）。

### 验证

- `tests/test_echo_change_task.py`：属性名精确比较（含**反证**：原版那种写法确实会误判）、
  语言门禁已清空（含反证）、「已经是目标属性」走跳过分支、跳过/失败分开统计、
  有限重试、以及三处接线对拍

## 抽卡记录分析

粘贴游戏里的「唤取记录」链接就能统计抽卡情况，界面参照**鸣潮工坊的抽卡分析**。

**⚠ 这是本项目唯一一个「联网读账号数据」的工具**，和其余工具**不是一类**：

| | 其它游戏工具 | 抽卡记录分析 |
|---|---|---|
| 工作方式 | UI 自动化（模拟点击 / 读屏） | **调库洛官方接口** |
| 需要管理员 | ✅ 要（UIPI 会拦低权限输入） | ❌ 不用 |
| 需要游戏开着 | ✅ | ❌ |
| 需要联网 | ❌（只拉 wiki） | ✅ **要**，且会把链接里的玩家参数发给库洛服务器 |
| 读游戏数据 | ❌ 不读写内存/存档 | 读**账号自己的抽卡记录**（官方接口，只读） |

### 怎么用

1. 点 **「获取抽卡记录」** —— 工具从本机游戏日志里读出链接并**自动填充**
2. 点 **「分析」**

> 自动获取失败（游戏没装本机 / 没登录过 / 日志里还没记录）时，
> 可以**手动**：游戏里 唤取 → 唤取记录 → 打开页面多翻几页 → 复制链接 → 粘到输入框。

#### 「获取抽卡记录」是怎么拿到链接的

鸣潮客户端会把**带参数的抽卡链接**写进日志：

```
<游戏目录>/Client/Saved/Logs/Client.log
```

日志整块是**混淆**过的，解密规则（逆向自同类工具，并在真实日志上验证过）：

```python
out[i] = b  if i < 3                                  # 前 3 字节原样
       = (b ^ 165) if (b & 1) else (b ^ 239)          # 其余按最低位选异或值
```

> ⚠ **必须整块解密，不能逐行**：日志里记录**不保证一行一条**。
> 我第一版按 `splitlines()` 逐行解密，结果 42663 行**一条都没匹配到**，
> 而整块解开立刻就找到了（`tests/test_gacha_link.py` 钉住了这个场景）。
>
> ⚠ 这条规则**不可自逆**（165/239 都是奇数，异或会翻转最低位）——
> 测试里造数据要用**真正的反函数**，不能偷懒套同一个函数。
> 我为此推错两次，最后改成**暴力穷举 256 个字节**验证。
>
> ⚠ 提取到的 URL 要**补回 `https://`** —— 匹配点在 `"url":"` 之后，
> 不补会得到 `aki-gm-resources...` 开头的残缺串。

找到游戏目录后会**记到用户数据目录**（`gacha_game_dir.json`），下次直接用；
找不到时才全盘扫（`where /r`，几十秒，所以放在后台线程）。

### 接口（2026-09-30 实测可用）

```
POST https://gmserver-api.aki-game2.com/gacha/record/query?<原查询串>&cardPoolType=N
Body(JSON): {serverId, playerId, languageCode, recordId, cardPoolId, cardPoolType}
```

> ⚠ **链接里的参数名和接口要的名字不一样**，必须做映射：
> `svr_id`→`serverId`、`player_id`→`playerId`、`lang`→`languageCode`、
> `record_id`→`recordId`、`resources_id`→`cardPoolId`。
> 直接拿链接的参数名去请求会 query 不到（见 `gacha.PARAM_ALIASES`）。
>
> ⚠ `code == -1` 通常不是网络问题，而是**记录过期 / 没打开唤取记录页** ——
> 提示要直接告诉用户"去游戏里打开唤取记录页再复制"。

**7 个卡池**逐个请求（接口一次只返回一个池）：角色活动 / 武器活动 / 角色常驻 /
武器常驻 / 新手 / 新手自选 / 新手自选（感恩定向）。

### ★ 历史记录（本地累积）—— 数字为什么会随时间变多

用户 2026-09-30 要求："这里怎么没有做持久化，按照时间保存为一个历史记录"。

**库洛接口只返回最近一段记录**（实测角色池给到 590 抽 / 约 3 周）。
所以每次「分析」都会把结果**合并进本地历史**（`gacha_history.json`），
数字随之变大 —— 鸣潮工坊能显示 4393 抽，就是这个道理。

**去重的身份键**（`:func:`gacha_store.record_key``）：

    身份 = (卡池类型, 物品名, 时间, resourceId)

> ⚠ **必须带 `resourceId`**：同一秒十连出两个**同名**物品时，
> 前三个字段会撞车，光靠它们会把其中一条当重复丢掉 —— 少一条抽数。
>
> ⚠ **不能用"时间 > 上次最新时间"过滤**：十连里 10 条时间戳完全相同，
> 严格大于会把同一次十连的后半截丢掉。

页面上「历史记录」列的是**每次拉取时累计到了多少**（含"本次新增 N"），
另有「清空历史」可以重置。

| 文件 | 内容 |
|---|---|
| `<用户数据目录>/gacha_history.json` | `records`（按身份键存全部记录）+ `snapshots`（拉取时间点） |

> 存盘用**临时文件 + 原子替换**：写一半断电也不会毁掉旧文件。
> 历史读写失败**不让工具不可用**（读不出来当空的、写不进去只记日志）——
> 历史是锦上添花，不该把工具页搞崩。

### 统计口径（★ 最容易算错的地方）

界面上的指标（对齐鸣潮工坊）：

| 指标 | 算法 |
|---|---|
| 总抽卡数 | 7 个池的抽数之和 |
| 平均出金 | 总抽数 / 五星数 |
| 五星数 | 五星总数 |
| 小保底不歪 | 限定池里 **UP 占所有五星的比例** |
| 每UP角色需 | 角色活动池 **总抽数 / 该池 UP 数** |
| 每UP武器需 | 武器活动池 同上 |
| 限定 / 常驻五星 | **只算角色**（见下） |

**★★ 两个"距离上次"的计数必须分开**（这是我第一版算错的根因）：

| 字段 | 含义 | 重置时机 | 用在哪 |
|---|---|---|---|
| `span` | 距离上一个**五星** | 每个五星都重置 | 列表里"这个金花了几抽" |
| `cumulative` | 距离上一次 **UP** | **只有出 UP 才重置** | 大保底 |

参考实现里那句 `a = t ? 1 : a + 1`（只有 UP 才重置）说的是
**大保底计数**；我一开始把它套到了显示用的"第几抽"上，
于是界面上会出现 `124抽` 这种**累计值**，明显不对。

- 接口返回的记录是 **最新在前**，`spans()` / `current_pity()` 都按这个方向写；
  搞反会让"第一金用了几抽"和"最后一金用了几抽"互换，**而且不报错**
  （`tests/test_gacha.py` 用双向构造把这个钉住了）
- **垫抽**（`current_pity`）= 最后一次出金之后又抽了多少（**从头部数**到第一个五星）
- **限定 / 常驻五星的统计只算角色**：反推验证 —— 工坊的
  `限定44 + 常驻19 = 63 = 五星数`，两数之和正好等于总五星数，
  说明统计的都是角色。把武器混进来会让两数之和超过总数。
- **欧非评价**：按平均出货抽数，`平均 >= 阈值` 归那一档，阈值从大到小匹配 ——
  所以**平均越小越靠表尾（越欧）**，最后一档阈值是 0，任何正数都有档位
- **常驻池没有 UP/歪**，`not_up_rate()` / `average_per_up()` 返回 `None`
  （不是 0 —— 0 会被显示成"0.0%"，读起来像"每次都歪"）

> ⚠ **`PERMANENT_CHARACTERS` / `PERMANENT_WEAPONS` 要维护**：
> 判定"歪没歪"靠的是"名字在不在常驻名单里"。鸣潮的常驻池会随版本**扩充**
> （新角色进常驻后要从名单里拿掉）。名单错了，不歪率和每 UP 均值全错，
> **而且不报错**（数字看着很正常）。

## 扫荡残像聚落

「展示当前版本所有的**残像聚落**和**梦魇残像**，以卡片形式展示，
可以一键勾选全部，勾选的运行后，**根据顺序一个一个去刷**」（用户 2026-10-13）。

### 和 ok-ww 原版 `NightmareNestTask` 的关系

**复用流程，换掉"刷哪个"的决定权。** ok-ww 已经实现了完整的一条龙：

```
开索拉指南 → 切页签 → 找到任意没打完的 → 传送 → 打 → 捡声骸 → 回到列表 → 再来
```

但它的取舍是「**刷所有**」—— `find_nest()` 只认行尾的 `0/24` 计数器，
**根本不看那行叫什么**。本工具要的是「只刷我勾的那几个、按我的顺序」，
所以继承它、把"选哪个"换掉，**传送 / 战斗 / 捡取一行都不重写**
（那些是最难调的部分）。

### ★ 三层定位：名称 → 别名 → 行号

光靠计数器认不出"这一行是不是我要的"（所有没打的都是 `0/24`）。
所以任务侧按可靠性依次退让：

| 层 | 判据 | 什么时候用 |
|---|---|---|
| ① 名称 | OCR 读行文字，和 `match_names` 比 | 常态（名称顺序变了也不怕） |
| ② 别名 | 同上，简称 / 少字时 | 名称对不上 |
| ③ 行号 | 按清单顺序点第 N 行 | 前两级都认不出来 |

三个判据全由数据文件提供（`SweepStep` 里带着），任务侧**不需要猜**。

> ⚠ ③ 数的是"**还没打完**的行"里的第 N 个，不是整表第 N 行 ——
> 刷过的行也占位置，按整表数会越点越偏。

### ★★ `_name_hit` 长的必须先命中

`梦魇·刺玫菇（稚形）` 和 `梦魇·刺玫菇` 是**两个不同的目标**。
短名是长名的子串 —— 拿短名先比，稚形那一行会被判成普通刺玫菇，
于是「勾了 A 却去刷了 B」，而**界面上完全看不出来**。

`SweepTarget.match_names()` 已经按长度倒序排好，但 `_name_hit` **自己又排了一遍**
（代价为零，漏排的代价是静默刷错）。`test_nest_sweep_task.py` 钉住了这条。

### 目标清单是一份**可编辑的数据文件**

```
<用户数据>/game_data/wuwa_sweep_targets.json
```

改它界面就跟着变，**不用改代码** —— 用户要的是"当前版本的所有聚落"，
而"当前版本"是会变的，写死在代码里意味着每出一版都要重新打包。
（和 `wuwa_set_versions.json` 同一套处理。）

> ⚠ **游戏里的官方写法是「残象聚落」（象，不是像）和「梦魇祓除」（祓，不是拔）**
> —— 官方版本公告原文如此，日文才是「残像集落 / ナイトメア祓い」。
> 本工具沿用用户和 ok-ww 的叫法（残像 / 拔除）做显示名，但 `aliases` 里
> **两种写法都放了**，匹配时不会因为一个字之差找不到那一行。

### ★★ 第 8 轮的「还是没对齐」= **列的 x 会漂**

#### 真实的数字（量我自己的渲染）

| 轮次 | 我量的 | 结论 | 为什么不够 |
|---|---|---|---|
| 4~5 | 卡片**高度**、名字/**勾选框**居中 | 「都对齐了」 | 没量套装区 |

> ⚠⚠ **这里有个坑，值得单独记：``widget.grab()`` 出的图比控件大。**
>
> 我第一版验证时拿 `card.grab()` 的图宽当卡片宽度算中心，得到
> "名字偏 +40px" —— 那是个**假偏移**：355px 的卡片 grab 出来是 **444px**
> （Qt 把阴影/外边距也画进去了）。要用 `mapTo()` 换到**同一坐标系**，
> 或者按 `控件宽 / 图宽` 的比例换算。
>
> 另外**勾选框指示器**是**青绿色**（teal，HSV 的 H≈90），
> 我只按"蓝色"(H 100-135)找会**一个都找不到**。

#### 勾选框为什么要垫一块 `CHECK_NUDGE`

`CheckBox("")` 的**指示器画在固定的左侧位置** —— 实测中心离控件左缘
`a ≈ 10.5px`，**与控件宽度无关**。而控件被 Qt 钳到 `W ≈ 29px`，所以
"控件居中"时**指示器偏左约 4px**。

`setFixedWidth` / `setContentsMargins` 都改不动它（位置由 paintEvent
直接算），只能在布局里**左侧垫一块**::

    S = W - 2a = 29 - 21 = 8

（推导：`控件左边 = (CW - S - W)/2 + S`，
要 `控件左边 + a = CW/2` ⇒ `S = W - 2a`）

> 验证同样靠**量**：把名字标签 / 勾选框各自 `grab()` 出来找可见像素的
> 中心，按比例换算回卡片坐标，10 张卡的偏移必须 **≤2px**
> （当前名字 ≤0.4px、勾选框 ≤0.5px）。

#### 「排列要整齐」= 套装区**固定高度**

各处的套装数量不等（**7 / 6 / 1 套** → 4 / 3 / 1 行）。不处理的话，
**每张卡的名字和勾选框会落在不同的 y 上**，三列并排就是参差的一排。

所以套装区固定成 `SET_ROWS = 4` 行高（`setFixedHeight`）——
套装少的那几张卡下面留白，名字就对齐了。

#### ⚠⚠ 「没修啊，还是不对齐」—— 固定高度**还有第二个坑**

第 4 轮做成固定高度之后，用户第 6 轮又标了一次「没修啊，还是不对齐」，

```

7 套的卡  图标 y = [17, 57, 98, 138]   行距 40, 41, 40
1 套的卡  图标 y = [20]                ← 起点还比别人低 3px！
```

**行距在漂** —— 根因有两个，都藏得很深：

1. **固定高度和实际内容高度对不上** → `QVBoxLayout` 会把差额**摊到各行**上。
   所以 `SET_ROW_GAP` 必须**精确**用进 `_sets_block_height()` 的算式
   （把算式和 `addSpacing` 里的魔数写成同一个常量）。
2. **单套的卡只有 1 行** → 差额 105px 全摊到那一行，把 chip 拉高，
   图标在 chip 里垂直居中就**往下跑了 4px**。
   修法：不足的行要补**等高的占位控件**，而不是只 `addSpacing`
   （那个不参与拉伸，摊不到它头上）。

修完之后：**所有卡第一行 y=14、行距恒为 35**。

## 打包成安装包

```
package.bat               # 双击即可。版本号自动取 src/app_config.py 里的 APP_VERSION
                          # （想临时指定别的：package.bat 0.4.0）
```

它做两件事：PyInstaller 出构建产物（中间目录）→ Inno Setup 出安装包。

**只改了 `installer\*.iss`（应用名、快捷方式、安装目录）时不必重跑 PyInstaller**：
双击 `dist\一键打包安装包.bat` 选 **2「只重出安装包」**，复用现有
`build\stage\WutheringWavesTools`，约 1~2 分钟（实测 1 分 53 秒，大头是 Inno 压 lzma2）。
它带**陈旧检查**：`src/` 比构建产物新就会把那些文件列出来拦下（要 `-Force` 才放行）——
因为那样打出来的包**不含最新代码**，而肉眼完全看不出来。

> `build\stage\WutheringWavesTools\`（构建产物）**别删**：删了就只能走完整打包，
> 而 `packaging\check_build.py` / `tests\check_frozen_fixes.py` 就是拿它当输入。
> 它在 `build\` 下，天生不进库，也不会被误当成产物发出去。

**产物（只有安装包）**

- `dist\WutheringWavesToolsSetup-<版本>.exe` —— 安装包，装到
  `%LOCALAPPDATA%\Programs\WutheringWavesTools`
  （安装本身免 UAC），带开始菜单 / 桌面快捷方式和卸载项。

> ⚠ **不再对外提供"绿色版"**（PyInstaller 的 onedir 目录）。它现在只是中间产物，
> 落在 `build\stage\`。`dist\` 里只应该有安装包 —— 想给别人装，给这个 exe 就行。
> 需要 Inno Setup 才能出包（`winget install --id JRSoftware.InnoSetup -e`）；
> 没装的话 `package.ps1` 会**直接失败**（而不是像以前那样"只出绿色版"然后报成功）。

**主程序要求管理员权限**（`packaging/mytools.spec` 里的 `uac_admin=True`）——
这是必须的，不是图省事：鸣潮带 ACE 反外挂，游戏自身以管理员运行，
低权限的本程序连一次点击都发不出去（见上面「前置条件」第 5 条）。
代价是**每次启动都会弹一次 UAC 确认**；如果账号不是管理员，程序会起不来
（那就得用管理员账号，或改回"普通启动 + 界面里一键提权重启"）。
安装包自身仍是按用户安装、不弹 UAC，只有启动程序时才会提权。

**用户数据不在安装目录里**：配置、任务流程、界面状态、探测产物都在
`%LOCALAPPDATA%\WutheringWavesTools\`（落点由 `src/core/paths.py` 决定），所以装到 `Program Files`
也能正常保存，卸载不会删用户配置，重装 / 升级也不会覆盖。开发态这些路径没变
（仍是项目根下的 `data/`）。

### 打包时的两个坑（都已处理，改配置时别踩回去）

1. **工具是靠 `pkgutil.walk_packages` 扫文件系统发现的**，而打包后代码在压缩归档里、
   磁盘上没有 `.py` —— 不处理会**一个工具都发现不到**：界面显示「工具（暂无）」、
   「已收录 0 个工具」，而且**不报错**。所以 `packaging/mytools.spec` 把
   `src/tools/**/*.py` 既收进归档（`collect_submodules`）**又当数据放一份**到 `_internal/`。
   （`registry.discover()` 里留了一条 warning 当报警器。）
2. **无控制台**（`console=False`）时 `sys.stderr` 是 `None`，日志等于直接丢掉。
   所以打包版会把日志写到 `%LOCALAPPDATA%\WutheringWavesTools\wutheringwavestools.log` —— 装机版出问题先看它。

**体积上的两个实测结论**（改依赖前先看这条，省得白折腾）：

- `opencv-python-headless` **并不比完整版小** —— OpenCV 5.x 两者 wheel 解压都是 112MB、
  `cv2.pyd` 都是 82MB（4.x 时代 headless 才明显更小）。试过一轮没收益，已还原。
- 打包后 344MB 里的大头：`cv2` 112MB、`PySide6` 74MB、`onnxruntime` 36MB、
  `assets` 30MB、`numpy`+`numpy.libs` 27MB、`onnxocr` 模型 21MB。

## 界面与图标

- **侧栏**：`主页` + `配置` + `工具` + `资源库`。**「工具」「资源库」都是可展开的分组**，
  展开后列出来的是各自的子项（工具名 / 各游戏的资源页），
  点工具名切到对应面板（框架的层级导航：分组项 `selectable=False`，工具项挂在它的 `parentRouteKey` 下）。
  分组**启动时是收起的**，只有从主页点卡片跳转时才自动展开、并把对应项高亮。
  **`配置` 和 `工具` 可以按住上下拖动换位置，「主页」固定在最上面**（框架不支持，自己实现的）；
  顺序存在 `data/ui_state.json`，下次启动照旧。
  左上角的菜单(☰)按钮已隐藏、折叠功能关闭；鼠标移到侧栏**右边缘**按住左右拖动即可调宽度
  （框架自带导航栏不支持拖拽，那条分隔条是自己加的）。
- **主页**：**不分分类**，所有工具平铺成一张**块状卡片**网格——上面图标、下面名称。说明文字**不常驻卡片**，
  鼠标悬浮时以小字提示弹出（走 `ToolTipFilter` 把延迟压到 120ms，Qt 默认 700ms 太慢）。
  点卡片会跳到对应工具，并**自动展开侧栏分组、把那一项选中高亮**。
- **工具面板**：懒加载。侧栏项挂的是 `ToolInterfaceHost` 空壳，第一次真正显示时才
  `create_widget()`（见 `main_window.py`），所以工具再多也不拖慢启动。
- **图标**：工具类里设 `icon_path` 指向一张图片即可（见 `EchoEnhanceTool`）。
  默认读 `assets/icons/<key>.png`，放一张 256×256 的 png 覆盖它就能换成自己的图标。

## 加一个新工具（三步）

1. 在 `src/tools/game/` 或 `src/tools/office/` 下新建 `xxx_tool.py`
2. 继承 `BaseTool`，用 `@registry.register` 装饰
3. 想有界面就重写 `create_widget()` 返回自己的 QWidget

```python
from ...core.categories import ToolCategory
from ...core.registry import registry
from ...core.tool_base import BaseTool

@registry.register(
    category=ToolCategory.GAME,
    name="骰子助手",
    description="自定义面数的随机数生成器",
    icon_name="GAME",
)
class DiceTool(BaseTool):
    key = "dice"

    def create_widget(self, parent=None):
        # 不重写的话，默认给一张「功能建设中」占位面板
        return MyOwnWidget(parent)
```

保存后重启程序，主页和侧栏「工具」分组里都会自动出现这个工具。

分类只影响**注册元数据**（工具页下拉框、占位页的「分类」一行）。

> ⚠ **主页不再按分类分组**（2026-09-24 按要求改成平铺所有工具）：新加分类**不会**让主页
> 多出一组卡片，新工具直接出现在那张平铺网格里。

## 踩过的坑（改界面时别重蹈）

这两个都是**深色 Windows 系统 + Fluent 组件**才会暴露的，写在这里省得再调一遍：

1. **别给 Fluent 窗口里的 `QTreeWidget` 套自定义 `setStyleSheet`。**
   自定义 QSS 会接管 item 的绘制流程，和 Fluent 的全局样式表打架，
   现象非常迷惑：数据和选中态都在（选中条能看见），**但一个字都不画**。
   树一律用 `compat.TreeWidget`（内部优先取 `qfluentwidgets.TreeWidget`）。
2. **`QScrollArea` / `QTreeWidget` 这类 Qt 原生容器会吃系统调色板底色。**
   深色系统上它们是黑底，套在浅色 Fluent 窗口里就是一块黑。
   解决：`self.setAttribute(WA_StyledBackground, True)` + `setStyleSheet("#某某 { background: transparent; }")`
   再补一句 `self.viewport().setStyleSheet("background: transparent;")`。
