# MyTools 阶段性总结

> 时间：2026-09-21 · 阶段：第 4 阶段（资源库资料真实化）

## 一句话现状

桌面工具集的骨架已经立住：**侧栏导航 + 工具插件机制 + 配置管理**三块都能跑、都有测试。
下面挂着一个真工具（声骸自动强化），它的**判定逻辑已验证、真实游戏联调还没做**。

## 已完成

### 1. 应用骨架
- **侧栏**：`主页 / 配置 / 工具`。工具是可展开的分组，工具项挂在分组下。
  「配置」和「工具」可**按住上下拖动换位置**，「主页」固定；顺序存本地。
  侧栏宽度可拖拽调整，左上角的菜单(☰)按钮已隐藏。
- **主页**：按分类铺块状卡片（图标 + 名称），点卡片跳转并自动展开侧栏分组、高亮对应项。
- **工具插件机制**：在 `src/tools/<分类>/` 下加一个带 `@registry.register` 的类，
  重启后主页和侧栏自动出现入口，**界面代码一行都不用改**。工具面板懒加载。

### 2. 声骸自动强化（`src/tools/game/echo_enhance/`）
五层分离，每层都能单独测：

| 层 | 文件 | 职责 | 状态 |
|---|---|---|---|
| 判定引擎 | `stats.py` | 词条定义 + 弃置/保留规则（零依赖） | ✅ 39 用例 |
| 画面读取 | `reader.py` | 截图 → OCR → 词条（属性名与数值按纵坐标配对） | ✅ 合成图实测 |
| 窗口控制 | `controller.py` | 定位游戏窗口 / 截图 / 键鼠 | ⚠️ 未联调 |
| 流程状态机 | `runner.py` | 培养 → 阶段放入 → 强化 → 读词条 → 判定 → 上锁/弃置 | ✅ 假窗口实测 |
| 配置界面 | `tool.py` | 配置卡片 + 运行/停止（QThread） | ✅ 实测 |

OCR 用 onnxocr（PaddleOCR v5 的 ONNX 版，模型自带 22MB）；合成图上识别准确率 99%+。

### 3. 配置管理（`src/core/loadout.py` + `src/gui/config_interface.py`）
- 一条配置 = 角色 + 声骸套装 + 4C/3C/1C 的声骸（**每档可多选**，每个声骸带一条属性）。
- 列表页：一条一条展示，支持**查看详情 / 修改 / 删除**（删除有二次确认）。
- 新增/修改弹框：角色可输入并实时过滤候选、头像联动、套装下拉带图标、声骸三档选择。
- 同一角色允许多条配置；数据存 `data/loadouts.json`。

### 4. 交互打磨
- **侧栏「配置」「工具」可按住上下拖动换位置**（「主页」固定），顺序存本地；
  侧栏宽度也可拖拽调整。
- **角色输入框：点一下就把候选摊开**，边打字边按内容过滤；一条都不匹配就收起，不留空框。
- **头像区**：「角色头像」标签 + 头像框（未选角色时空白）+ 「更换」按钮（挑自己的图；
  再换角色会清掉自定义头像、回归联动）。
- **包一层可复用的选择控件**（`src/gui/pickers.py`）：可输入过滤下拉 / 带图标下拉 /
  单选属性组 / 声骸选择行 —— 以后别的界面直接用。

### 5. 资源库资料真实化（第 4 阶段）

**角色名单和套装效果是从公开 wiki 整理来的，不再是编的**：

- 58 个角色（名字 + 稀有度 / 属性 / 武器）、34 套声骸套装（名称 + 2/5 件套效果原文）
- 数据放在 `src/core/data/*.json`，每个文件带 `_source` / `_fetched`；
  页面顶部也写明「整理自公开 wiki，抓取于 X（游戏版本 Y）」
- `tools/refresh_wuwa_data.py` 能从 bwiki 重新抓取（按套装名 merge，**不动声骸明细**）
- **图标仍是自绘占位图** —— 官方美术素材不做打包，你自己放同名文件即可替换

数据管线：`JSON → game_data.py（加载 + 查询）→ 界面`，界面代码不写死任何一条资料。

## 已知风险

1. **游戏联调是最大的未知**。判定规则、OCR 解析、流程逻辑都有测试兜底，
   但"点在屏幕的哪个位置、游戏认不认"这部分完全是空白。第一次跑建议先把
   `tool.py` 的 `dry_run` 改回 `True` 走一遍。
2. **游戏版本更新会让模板/坐标失效**，这类工具天生要跟着版本维护。
3. **合规**：ok-ww 的 README 自己贴了封号警告（官方把自动挂机列为违规）。
   这个工具是你自己用的，但风险摆在这儿。
4. 3C/1C 每档目前只能选"一个代表性声骸"，游戏里实际要带两个 —— 配置模型支持多选，
   但语义上还没跟游戏的真实搭配对齐。
5. **资料会过期**：角色 / 套装抓的是游戏 3.6 版，出新版本后要重跑
   `tools/refresh_wuwa_data.py`。抓取脚本依赖第三方 wiki 的页面结构，改版就得改正则。
6. **图标仍是占位图**，与游戏内观感有差距；素材得你自己提供。

## 关键技术决策

- **分层**：`core/` 不依赖 Qt（所以能命令行单测），`gui/` 只碰 Qt，`tools/` 放实现。
  这条线守住了，测试才好写。
- **资料数据与代码分离**：角色 / 套装放在 `src/core/data/*.json`（不再写死在 .py 里），
  每个文件带 `_source` / `_fetched`，界面顶部也显示出来 —— 让人一眼看到这份资料的
  出处和时效，而不是把第三方整理的内容伪装成权威数据。
- **兼容层**：`gui/compat.py` 把"第三方库名字改了"的风险关在一个文件里，
  图标名和控件类名都走多级降级。
- **存储容错**：配置文件损坏 / 缺字段 / 格式变过（声骸从单条变列表）都不抛异常，
  只跳过能跳的。

## 走过的弯路（都记在 `README.md` 和工作区记忆里）

- `qfluentwidgets.ComboBox` **不显示 item 图标** → 套装下拉是用 `PushButton` + `RoundMenu` 自己拼的。
- `EditableComboBox` 不做候选过滤，回车还会把无匹配内容塞进候选列表 → 子类覆盖。
- `ScrollArea` 的深色底要三件套才能治（`WA_StyledBackground` + 自身样式 + viewport 样式）。
- `MaskDialogBase` 必须有 parent，否则构造就崩。
- 弹框截图要把子窗口先清掉，否则会被画进整窗截图里。
- **弹层 BUG 连环两起**（都是"能弹出来但用不了"）：
  1. 框架菜单是 `Qt.Popup`，会 `grabKeyboard()` → 候选弹出来了但**打不了字**；
     去掉 Popup 后又引入
  2. 点菜单会让菜单窗口激活、输入框失焦，而"失焦即关闭"抢在点击之前把菜单关了 →
     **点了候选没反应**。最终靠 `WindowDoesNotAcceptFocus`（菜单连焦点都不接受）解决。
- **省事的验证方式连续骗过我两次**：用 `setText()` 验输入（绕过键盘通路）、
  直接给菜单子控件发点击（跳过窗口激活）。→ 定成规矩：**验"能不能用"必须复现真实事件链**，
  键盘用 `QTest.keyClicks` + `keyboardGrabber()`，弹层点选先 `setFocus()` 模拟激活再点。
- **QLabel 自动换行的高度在嵌套布局里必然算不准** —— Qt 的 `QBoxLayout` **不传播**
  `heightForWidth`，父布局会把卡片压掉几像素，表现是「最后一行文字被裁掉一半」。
  解法：给 label 固定宽度 + 给卡片 `setFixedHeight(layout().totalSizeHint().height())`。
  这个坑是靠"断言卡片高度 ≥ sizeHint 高度"抓出来的，肉眼只看截图容易当成渲染伪影。

# 第 5 阶段总结（2026-09-22 · 资源库资料化 + 任务系统）

## 一句话现状

MyTools 从"单工具"长成了"平台"：**资源库资料化了**（官方数据源接入、图鉴、自动更新工具），
**任务系统落地**（流程编排 + 顺序执行 + 运行控制），配置的属性判定升级为多选。
真实游戏联调仍然是未踩的雷区。

## 这一阶段做了什么

### 1. 鸣潮资源库资料化
- **官方数据源接入**：库街区 wiki 的 `getPage` 接口（POST form，请求头 `wiki_type: 9`，
  `catalogueId=1107`）一次拉全 199 条声骸记录 + 标签树。tagTree 是 **dict** 不是 list，
  套装标签只认「套装」分组下的 34 个子节点（COST / 级别 / 异相都是同级分组，别混）。
- **声骸掉落池补全**：bwiki 的 138 条是官方 181 条的严格子集，并集合并后 34 套 4C/3C/1C 全齐
  （碎梦亡鬼之魇是 1 件套，只有 4C 是对的）。合并一律取并集，任何一边刷新都不冲另一边。
- **资源库页面**：三个分区（角色头像 / 声骸套装 / 声骸图鉴）都套了折叠卡片；
  声骸图鉴按 4C/3C/1C 分组，每行 图标 + 技能说明（来自 bwiki 声骸页解析，138/181，
  43 个新声骸 bwiki 还没建页；库街区详情接口要登录令牌，实测假 token 直接 500）。
- **真图标**：库街区记录自带官方图床 URL，替换占位图的判据是
  "import 占位图脚本重画一张对比字节"——字节一致才覆盖，真图零风险。

### 2. 新分类「数据」+ 鸣潮资源库更新工具
- 新工具分类 `DATA`（数据），主页自动分组。
- 工具面板：打开即后台检查（QThread，3~4 个轻量请求，不写盘）→ 有更新则提示 +
  变更摘要 + 「获取最新数据」点亮 → 点击应用（效果替换 / 掉落池并集 / 新声骸补技能）→
  提示重启生效。核心逻辑在 `src/core/wuwa_update.py`（无 Qt，命令行可单跑）。

### 3. 任务系统（本期主体）
- **侧栏新增「任务」页**（主页 / 配置 / 任务 / 工具 / 资源库，可拖动排序）。
- **任务流程模型**（`src/core/tasks.py`，无 Qt）：流程 = 名字 + 任务类型 + 有序步骤；
  步骤分「工具」和「配置」两种，配置挂到它上面最近的工具下，悬空配置保存时丢弃并提示。
  存储 `data/tasks.json`，容错同配置管理。
- **编排弹框**（`task_editor_dialog.py`）：左侧可用组件（支持任务运行的工具 + 角色配置）、
  右侧流程列表，**QListWidget 原生拖拽**（左拖右添加、右内拖排序），
  保存前校验（名称必填、至少一个工具步骤）。
- **任务页**（`tasks_interface.py`）：每行一条流程，操作有 详情 / 修改 / 删除 / 运行 / 停止。
  运行用 QThread 按顺序跑，**同一时刻只允许一条流程**（都要抢游戏窗口）；
  停止是协作式的（当前动作结束后退出）。
- **工具运行钩子**：`BaseTool.create_task_runner(options, log, should_stop)` +
  声明式 `supports_task_run` 标记（编排界面靠它列可用组件，不实例化探测）。
  声骸自动强化已实现（默认判定配置；挂的配置仅记录——强化判定本不吃角色配置）。

### 4. 配置属性多选
- 一条声骸的属性框从"复选框外观、单选语义"改成**真多选**。
- 模型 `EchoPick.stat: str` → `stats: tuple`，旧 JSON（含旧词条「属性伤害加成」）全部兼容读出；
  控件去互斥、弹框收集/回填/详情全链路跟着改。

### 5. 任务类型（两级下拉）
- 一级**直接复用工具分类**（`ToolCategory`：游戏 / 数据 / 办公）——加一个工具分类，任务类型下拉自动多一项，不用两头改；二级是「具体产品 / 场景」（游戏 → 通用 / 鸣潮）。
  候选表 `src/core/task_types.py`（无 Qt），**支持一个新游戏就加一行**。
- 一级另有「未分类」（key 为空串）：老流程 JSON 没有类型字段，编辑时落在这里；此时二级下拉置灰并提示「先选任务类型」。
- 流程**只存 key 不存显示名**（改名 / 挪分类不影响老数据），`TaskFlow.__post_init__` 做规范化（坏 key → 未分类 / 通用）。
- 按需求，任务类型**只是流程的标签，不过滤可用组件**；列表行在名字右侧显示「游戏 · 鸣潮」，未分类不显示标签（不增卡片高度）。

### 6. 任务流程「开始」步：客户端检查 + 开背包准备

- 「开始」以前只是个**视觉标记**（不执行任何东西），现在是真的第一步：
  `core/task_start.py` 按**任务类型**做前置检查 —— 类型是游戏就按二级选的具体游戏
  （游戏 → 鸣潮）查客户端是否在运行，**没启动直接报错、任务停止**；
  未分类 / 数据 / 办公跳过；类型是游戏但二级选了「通用」则警告跳过（不知道查谁）。
- `core/game_client.py`（无 Qt）：判据两条**任一命中**即算已启动 ——
  ① 窗口标题含关键字（和 `controller.WINDOW_KEYWORDS` 同一套，有单测钉死一致性）；
  ② 进程名 `Client-Win64-Shipping.exe`。进程枚举用 **ctypes 直调 kernel32**，
  因为本机 pywin32 312 **没有** `QueryFullProcessImageName`（详见「新踩的坑」）。
- **准备动作**走新钩子 `BaseTool.create_task_prep`：流程跑到「开始」时问每个工具
"要不要先把环境摆好"，第一个声明了的执行（`tools/.../prepare.py`：按 B 开背包 →
（校准后）切声骸页签 → 开过滤器 → 按等级排序）。
- ⚠ **只有「按 B 开背包」是已校准的**。游戏里那几个按钮的文字/位置没有真实界面数据，
  `PREP_STEPS` 里标了 `verified=False`：默认**跳过、绝不乱点**（猜错坐标可能触发分解），
  同时自动跑**探测**，把当前画面 + OCR 每一行的文字/相对坐标/像素坐标落到 `data/probe/`，
  拿它就能把那三步填成真点击。工具页也加了「探测背包界面」按钮随时可跑。
  参考实现 ok-ww 同样没做这几步（它的说明就是让用户手动筛），不是漏抄。

### 7. 「4C 自动战斗」—— ok-ww 引擎整段搬运（0.3.0）

> 需求变更说明：第一版做的是"行为兼容"（自己写检测/循环），用户明确要求
> **保持与 ok-ww 一致、照搬它的功能**；询问后确认走"整段搬运 + AGPL 合规"。
> 第一版自研的 detect/rotation/runner 已全部删除。

### 方案

- ok-ww 的战斗引擎不可手写复刻：`BaseCombatTask` 50+ 方法、`BaseChar` 1025 行、
  53 份角色脚本、COCO 模板框架、OCR 读 CD —— 直接 **vendor 官方源码**（master 分支）：
  `vendor/okww/` = `okww/`（原 `src/`，包名改写 src→okww，212 处导入逐模式计数替换）+
  `config.py` + `assets/`（模板图 + 37MB YOLO 声骸模型）+ `i18n/`。
- ok-script 框架**不用搬**：它是 PyPI 包（ok-ww requirements 指定 2.0.7b1），
  pip 装进 venv 即可；MyTools 现有依赖与之高度重合（onnxocr-ppocrv5 /
  fluent-widgets 1.11.3 / shapely 全都已在）。
- 嵌入方式：**headless 运行时**。ok-script 原生支持（`resolve_ui_config` 无 gui →
  HeadlessApp + StartController），宿主 `okww_boot.OkwwHost` 在后台线程
  `OK(config)` → `start_controller.do_start(task)`；停止走
  `executor.stop_current_task()`（**不能调 `OK.quit()`**，它在 headless 下也会碰 Qt）。

  `interaction='PostMessage'`（后台按键不抢前台）等 windows 配置原样保留

## 安全边界：运行时碰了游戏的什么

（2026-09-22 逐项排查。结论：**不读、也不修改游戏进程内存**。）

| 类别 | 状态 | 证据 |
|---|---|---|
| 进程内存读写 | ❌ 无 | 全项目搜 `ReadProcessMemory` / `WriteProcessMemory` /
`VirtualAllocEx` / `VirtualProtectEx` / `CreateRemoteThread` / `SetThreadContext` /
`MiniDumpWriteDump` / `PROCESS_VM_*` / `PROCESS_ALL_ACCESS` —— **0 命中**。唯一一处
`OpenProcess` 在 `core/game_client.py`，权限是 `PROCESS_QUERY_LIMITED_INFORMATION`
（只够问"这个 pid 的可执行文件叫什么"，拿不到地址空间） |
| 注入 / 钩子 / 驱动 | ❌ 无 | `SetWindowsHookEx` / `LoadLibrary` / `DeviceIoControl` → 0 命中 |
| 内存类依赖 / 夹带二进制 | ❌ 无 | 依赖只有 mss / opencv / onnxruntime / onnxocr / pywin32 / shapely；
仓库里没有任何 `.dll` / `.pyd` / `.exe` |
| 第三方实现 | ❌ 未引用 | ok-ww 只在注释里作为**思路参考**出现，没有 import、没有拷贝其代码 |
| **屏幕像素** | ✅ 读 | `mss` 抓屏（GDI `BitBlt`，源是整屏 DC）→ 交给 OCR 认字（`controller.py`） |
| 窗口元数据 | ✅ 读 | 窗口标题、客户区几何（`controller.py`） |
| 进程信息 | ✅ 读 | 进程名列表 + 目标 exe 文件名，只用于比对（`game_client.py`） |
| **键鼠输入** | ✅ 发真实前台事件 | `mouse_event` / `keybd_event`（`controller.py`）—— 游戏收到的是"真实玩家操作" |
| 游戏文件 | ❌ 不碰 | 项目所有读写都在自己的 `data/` / `assets/` 下，没访问游戏安装目录或 AppData |
| 网络 | ✅ 只访问 wiki | `wiki.biligame.com` + `api.kurobbs.com`（图鉴数据），与游戏进程无关 |

两条要留意（**不是**"读内存"，但属于已知影响面）：

1. 它**靠 OCR 认字**而不是读内存 —— 这正是坐标必须校准的原因；
   （真读内存的作弊工具根本不需要截图和 OCR。）
2. 所有动作都**走游戏自己的 UI**（点按钮 / 按 C 上锁 / 按 Z 弃置），等价于你手点。
   但"自动化操作"在多数游戏的服务条款里另有规定，是否违规取决于厂商政策 ——
   本项目不做这个判断。另外**按 Z 弃置不可逆**（真分解声骸），用之前留意那个开关。

# 第 6 阶段总结（2026-09-23 · 装机版四个问题的修复）

## 一句话现状

把安装包在**另一台电脑**上跑通时暴露的四个问题全部修掉：
① 提权（游戏在管理员权限下，工具不发提权就一点都点不动）；
② 首启动资源库空白（种子数据播种晚于数据模块导入）；
③ 声骸强化只跑一次（「培养」被塞进了每次强化的循环里）；
④ 任务流程没按工具页配的规则筛选（跑的是代码里的默认判定）。

## 1. 启动即以管理员运行（新增 `src/core/elevation.py`）

**病因**：鸣潮带 ACE 反外挂，游戏进程是 **High 完整性级别**；Windows 的 UIPI 禁止
低完整性进程向高完整性窗口注入输入 —— `SetCursorPos` / `mouse_event` 直接失败
（`(0, 'SetCursorPos', 'No error message is available')`），`keybd_event` 则是**静默丢弃**。

**修法**：

- `packaging/mytools.spec` 加 `uac_admin=True` → exe 清单要求 `requireAdministrator`，
  双击就弹 UAC 以管理员启动（实测：不提权启动会直接 `WinError 740 请求的操作需要提升`）；
- 新增 `core/elevation.py`：查自身提权状态 / 目标进程完整性级别（`TokenElevation` /
  `TokenIntegrityLevel`）、`ShellExecuteW("runas")` 一键提权重启、以及把
  `(0, 'SetCursorPos')` 这类报错翻译成**可操作**的提示；
- `controller.GameWindow.verify_input_allowed()`：运行前比一次完整性级别 + 做一次
  无副作用的真实探针（`SetCursorPos(当前坐标)`），不通过就抛 `InputBlocked`，
  不再"开始运行 → 第 1 次强化 → 出错"；
- `bring_to_front()` 改成**返回是否真的置前**并在调用处记警告（它以前静默吞失败，
  正是"探测截到的是 MyTools 自己"的原因）。

## 2. 首启动资源库空白 + 检查结果自相矛盾

**病因**：`main.py` 里 `from src.gui.main_window import MainWindow`（连带导入
`core.game_data`）发生在 `paths.ensure_user_data()` **之前**。首启动时用户数据目录还
不存在，`game_data` 在 import 那一刻把**空数据**快照进内存，之后再拷种子也不会重读。
而「鸣潮资源库更新」读的是**盘上的文件**（那一刻已被拷好）→ 于是它诚实地说"已是最新"。
一个看内存、一个看磁盘，两边看着矛盾。

**修法**：

- `main.py`：`ensure_user_data()` 提到**任何 `src.*` 子模块导入之前**
  （`tests/check_frozen_fixes.py` 会按 AST 断言这个顺序，防止以后又被改回去）；
- `game_data`：公用清单改成**可变容器 + `reload_data()` 就地刷新**
  （别的模块是 `from ... import CHARACTERS` 把名字拿走的，重新赋值模块属性它们看不到）；
  新增 `DATA_VERSION` / `ensure_loaded()`；
- 资源库页 `ensure_loaded()` 兜底 + **按数据版本自动重建**（`rebuild()`），
  所以"获取最新数据"之后**不用重启程序**；
- `check_updates` 说实话：远端一条数据都没拉到时报「没能取到远端数据」而不是
  「已是最新」（以前那等于"什么都没查到却说没事"），本地为空也单独提示；
- 命令行入口 `wuwa_update.main()` 同样先 `ensure_user_data()`。

## 3. 只强化一次就停

**病因**：`_enhance_once()` 每次强化都先点「培养」，而「培养」**只在声骸列表页存在** ——
第 2 次强化时人已经站在强化界面，5 秒超时后抛错退出。

**修法**：拆成 `_enter_enhance_panel()`（每个声骸**一次**，连点「培养」直到它消失）与
`_enhance_one_stage()`（每次强化一次，只做「阶段放入 + 强化并调谐」）。
另外：出错时**尽力按 ESC 把画面收回列表**（否则下次运行直接报"没检测到声骸面板"，
用户得自己按 ESC）；`_back_to_list` 加了 ESC 次数上限（兜底动作不能无限按）；
弹窗匹配从 3 字前缀收紧成完整短语。

## 4. 任务流程没按配置筛选

**病因**：`create_task_runner()` 里硬写 `JudgeConfig()` —— 代码里的默认值。
于是"从任务页跑"和"从工具页点运行"用的**不是同一套规则**，
用户在界面上配的核心属性 / 双爆下限 / 有效词条数全都没生效。

**修法**：

- 新增 `core/tool_settings.py`（用户数据目录下的 `tool_settings.json`，按工具 key 分节，
  临时文件 + `replace` 原子写）与 `echo_enhance/settings.py`（`EchoSettings` ↔ `JudgeConfig`，
  每个字段都容错：手改坏的 / 旧版本的值一律落回默认或夹到合法范围）；
- 工具页**每次改动即存盘**，打开页面时回填；
- `create_task_runner()` / `create_task_prep()` 读这一份，并把实际规则写进日志
  （`判定配置（取自工具页保存的设置）：核心 … / 暴击≥… / 有效词条 ≥…`）。

## 测试基线（全绿）

- 单测 **224 个**（本阶段 +32：`test_elevation` 9 / `test_echo_settings` 15 / `test_first_run` 8）
- 冒烟 4 个：`smoke_core` 13/13、`smoke_gui`、`smoke_echo_runner`（**新增"一个声骸只点一次培养"、

## 本阶段新踩的坑

1. **ctypes 不声明 `argtypes` 会在 HANDLE 上炸**：`OverflowError: int too long to convert`，
   报错指向"参数 1"，看着像调用方传错了。DLL 原型要一次钉齐。
2. **SID 函数在 `advapi32` 而不是 `kernel32`**：`GetSidSubAuthorityCount` 拿错 DLL 会
   `AttributeError: function not found` —— 而且只在真去取完整性级别时才炸。
3. **`is_elevated()` 返回 False 不等于实现坏了**：我的第一反应是"取不到令牌"，
   其实是本机真的没提权。查这类 API 要拿"已知存在的目标"做肯定分支

4. **占位/游离控件截图是空白**：`tool.create_widget(win)` 建出来的页面没进任何布局，

5. **`QShowEvent` 得是真的**：拿 `type("E", (), {})()` 冒充事件对象，
   `super().showEvent()` 直接 TypeError。

# 第 7 阶段总结（2026-09-23 · 4C 自动战斗）

## 一句话现状

新增第三个工具 **「4C 自动战斗」**：检测到进入战斗后按配置输出（普攻 / 共鸣技能 /
声骸技能 / 共鸣解放），脱战停手、可选按 F 拾取、可连打多场；带**干跑**模式校准检测阈值。
传送 / 开副本 / 打完重开这三步**没做**（原因见下）。

## 1. 先把 ok-ww 的真实数据挖出来

「4C」在 ok-ww 里 = **4-Cost（Boss）声骸**，对应 `FarmEchoTask`
（`'🌀 Farm 4C Echo in Dungeon/World'`）。它的源码只剩 `__pycache__`，于是用
`marshal` 读 `.pyc` 的常量，拿到这些**真实参数**（不是猜的）：

* 按键：`Game Hotkey.json` → 共鸣技能 `e`、共鸣解放 `r`、声骸技能 `q`、
  闪避 `lshift`、跳 `space`、轮盘 `tab`、背包 `b`；
* 普攻 = 反复 `task.click()`，间隔 **0.1 秒**（`click_with_interval`）；
* 战斗判定：`CombatCheck`（`has_health_bar` / `target_enemy` / `check_f_break`），
  用 `find_color_rectangles` + `get_mask_in_color_range`，颜色名 `enemy_health_bar_red`；
* 战斗引擎：`BaseCombatTask`（CD 靠 OCR 读技能图标、切人有 intro/buff 计时、
  复活兜底…）+ `src/char/*.py` **53 份角色脚本**（另有 2 份在 `repo/src/char/`）。

**结论：照搬不了**。ok-ww 的战斗依赖它自带的**图像模板图**（`working/assets/images`，
本机只有 1 张，其余没落盘）+ 每角色脚本 + 引擎里的一堆状态机；搬到别处等于重写它。

## 2. 于是做成"同样的结构、更简单的判据"

| | ok-ww | 本工具 |
|---|---|---|
| 战斗判定 | 图像模板 | **颜色规则**：区域红占比 + 最长横向红条（两条同时成立） |
| 技能可用性 | OCR 读 CD 数字 | 到最短间隔就放；可选图标区域 + 亮度阈值（= ok-ww 那条思路的简化） |
| 每角色循环 | 53 份脚本 | 一张可配技能表（默认 E → Q → R） |
| 传送/进副本/重开 | 有 | **没做**（需要真实界面素材） |

新增 `src/tools/game/auto_combat/`：`detect.py`（判定，纯逻辑）、`rotation.py`
（决策，纯逻辑）、`settings.py`（设置持久化）、`runner.py`（循环 + 干跑）、`tool.py`（界面）。

顺带扩展了 `controller.py`：`mouse_down/up`、`click_here`（**不移动光标**的点击 ——
动作游戏里移动光标可能带动视角）、`move_to_client_center`（ok-ww 也有这个复位动作），
以及 `lshift/t/f1/数字` 等按键。

## 3. 复用带来的两件事

* **控件搬家**：`NumberField / NumberStepper / ConfigCard` 从 `echo_enhance/tool.py`
  挪到 `src/gui/widgets.py`（两个工具共用一套），echo 那边改成导入，行为不变；
* **搬家搬出一个真 bug**：`_fmt_number` 原来写死 `f"{value:.1f}"`（一位小数），
  用在暴击下限（7.5）没问题，但检测区域（0.22）和阈值（0.015）会被四舍五入吃掉 ——
  改成按字段自己的 `decimals` 格式化再裁零，整数仍保留一位小数（`15.0`）。
  **教训：复用控件时要查它写死的格式/范围假设。**

## 测试基线（全绿）

- 单测 **252 个**（本阶段 +28：`test_combat_detect` 15 / `test_combat_rotation` 13）
- 冒烟 5 个 + 检查脚本 3 个（新增 `check_combat_gui.py`、`smoke_combat_runner.py`）
- `smoke_combat_runner` 用**假窗口 + 假时钟**跑 7 个用例：进战/脱战/拾取、干跑不按一键、
  等不到战斗、外部叫停、权限不足、最长时长强制收手、连打两场
  ★ 假时钟的坑：步长别取太大 —— 等待循环里"读表本身"也在推进时间，
  0.5 秒步长 + 2 秒超时只跑了 1 次迭代，表现为"等不到战斗"。

## 本阶段新踩的坑

1. **第三方 pyc 挖参数**：`python 3.13` 的 `dis` 反汇编 3.12 的 pyc 会 `CACHE` 报错，
   但 **`co_consts` / `co_names` 照样能读** —— 阈值、坐标、文案都在里面；
   另外**先去翻配置文件 JSON**（ok-ww 的 `configs/*.json` 直接给了按键与开关），
   比反汇编省事得多。
2. **`mss` 抓的帧是 BGR**，红色在最后一个通道 —— 颜色判据写错通道会"永远不命中"。
3. **假窗口假时钟**是测"时序 + 状态机"的正解：不用真 sleep，还能确定性复现
   "进战→输出→脱战"这种需要几十秒的流程。

# 第 9 阶段：声骸自动强化改用 ok-ww 引擎（2026-09-23）

MyTools 原来自己写了一套点击/OCR（`controller.py` / `reader.py` / `prepare.py` /
`runner.py`，共 ~1300 行）。同期的「4C 自动战斗」走 vendored ok-ww 引擎是跑通的 ——
同一件事有两套实现，那就只留跑得通的那套。

* **搬**：整个 `okww.task.EnhanceEchoTask` 的流程（培养 → 阶段放入 → 强化并调谐 →
  关弹窗 → OCR 词条 → `Z` 弃置 / `C` 上锁 → 找下一个 0 级声骸），
  坐标 / 模板 / OCR / 后台按键全是 ok-ww 原样。
* **不搬**：ok-ww 自己的筛选规则（必须有双爆 / 双爆总计 / 首条双爆 /
  第一条必须为有效词条 …），换成 `stats.judge()` 那套
  （核心属性 / 可选属性 / 双爆各自下限 / 满值保护 / 有效词条数）。

## 关键实现：三态怎么映射回 ok-ww 的布尔

ok-ww 的判定入口只有一个方法，返回布尔：

```python
check_echo_stats(properties, values) -> bool     # True=继续强化，False=弃置
```

于是**只 override 这一个方法**就够，主循环一行都不用改：

| `judge()` 的动作 | 返回 | ok-ww 侧的落点 |
|---|---|---|
| `discard` | `False` | 按 `Z` 弃置 |
| `continue` | `True` | 继续强化 |
| `lock` | `True` | 主循环里 `len(properties) >= 5` 时上锁 |

`lock` 映射成 `True` 不是偷懒：MyTools 的 `lock` **只在词条满 5 条时**才出现，
而 ok-ww 恰好就在那个时刻上锁 —— 两条路的落点一致。
「满值保护」返回的是 `continue`（继续强化到满级再上锁），语义也正好对得上。

## 两处"不照抄"的地方（有意为之）

1. **配对前先剔掉认不出的属性名**。ok-ww 只过滤了「辅音」，剩下任何 OCR 噪声都会
   "吃掉"一个数值，让它后面所有属性名**整体错位一格** —— 数值配错，判定自然是错的。
   `judge()` 本来就只认标准词条，提前剔掉是纯收益。
   （单测 `test_unknown_names_do_not_consume_values` 专门盯这条。）
2. **屏蔽 `os.startfile`**。ok-ww 在任务结束且成功过至少 1 个时会
   `os.startfile('screenshots')` 帮你打开截图文件夹 —— 它自己是 GUI 工具这么做没问题，
   MyTools 里是后台工具，无缘无故弹资源管理器窗口很突兀。用
   `_no_startfile()` 上下文包住 `run()` 即可，不影响截图落盘。

另外把 ok-ww 的 `Pause after Success` 默认改成 `False`：
它原版「成功即暂停」是给"边看边强化"准备的，批量工具暂停会表现得像
**"只跑一个就停了"**（正是用户会误以为坏掉的那种现象）。
⚠ `default_config` 是在 `after_init → load_config` 时才变成 `self.config` 的
（`ok/task/task.py`），所以在子类 `__init__` 里改默认值是生效的。
