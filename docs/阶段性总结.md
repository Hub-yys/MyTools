- **工具插件机制**：`src/tools/<分类>/<工具>/` 下加一个带 `@registry.register` 的类，

- **应用图标**：`assets/app.ico`（`tools/make_app_icon.py` 生成），
  任务栏 / 托盘 / 安装包统一用它。

### 4. 配置管理 + 资源库

**配置页有两类配置**（09-26 成型，见「第 16～19 阶段」）：

| 类型 | 存哪 | 内容 | 现状 |
|---|---|---|---|
| **角色声骸筛选配置** | `data/loadouts.json` | 角色 + 套装 + 4C/3C/1C 声骸（每档多选） | 原有 |
| **角色声骸强化配置** | `data/echo_profiles.json` | 一套**强化判定条件**（核心属性 / 可选属性 / 双爆下限 / 有效词条数 / 满值保护） | 只存不接入运行 |

* 列表里显示成 **`绯雪-声骸筛选` / `绯雪-声骸强化`**（类型后缀，只加在显示上，
  存盘仍是纯角色名 —— 否则头像查不到、下拉也回填不了）。

「角色声骸强化配置」的编辑界面**就是强化工具页那份设置区**（同一个组件），
但两者**互不影响**；新增时的起点是**出厂默认**（＝打开工具页每次看到的那套）。

资源库：58 角色 / 34 套装 / 181 声骸的公开 wiki 资料（`src/core/data/*.json`，
每个文件带 `_source` / `_fetched`），可由 `资源库更新` 工具重抓。
**游戏素材**已随包：58 头像 + 34 套装图标 + **181 声骸图标（全了）**；ok-ww 的模板图与
`echo.onnx` 走 `vendor/`（被 .gitignore 排除，克隆后需自己取）。

### 5. 交互打磨（09-25 / 09-26 集中做的）
- **托盘常驻**：缩到托盘时工具/任务**继续执行**；托盘菜单可叫回窗口
- **关闭确认**三出口：隐藏到托盘 / 直接退出 / **X·Esc = 取消**（误按代价最小）
- **有任务在跑时关闭**：点明**是哪个工具/任务**在跑，再问「停止并退出」
- **点运行后**：自动退到后台 + 把游戏切到前台
- **核心 ↔ 可选属性联动**：进了核心的词条在可选里**置灰且不可勾选**

### 6. 任务流程（把工具串起来跑）
- 一条流程 = **名字 + 有序的步骤**；步骤有 工具 / 配置 / 开始·结束标记四类；
  配置挂在**它前面最近的工具**下（运行时把配置名与 key 传给工具）。
- 编排界面：可用组件（**全部 4 个工具 + 两类配置**，带图标）拖到下方编排区，
  支持**按落点在中间插入**（拖到两项之间就插在那儿，有蓝色竖线指示）
  + 内部拖动排序 + 搜索（中文 / 拼音）。配置项的名字**跟配置页一致**
  （`绯雪-声骸筛选` / `绯雪-声骸强化`），且**每次都去配置里读最新的**。
- **「任务类型」不需要手选**（2026-09-26 去掉）：从流程里的工具**推导**，
  「开始」步据此决定要不要检查游戏客户端在不在跑。
- 配置在流程里存的是 **key**（筛选配置 = id、强化配置 = 稳定 id），
  名字只在配置里有一份真身 —— 配置改名，流程里那一步跟着变。
- **「详情」显示的是流程图**（图标 + 名字 + 箭头的横向链条，只读），
  和编排区共用同一套瓦片（`FlowPreview` / `make_flow_list`）。
- ⚠ **配置要放在工具后面**才算挂上：`tool_bindings()` 只认"前面最近的工具"，
  排在前面的配置**运行时不会绑给任何工具**（保存时会弹提示说清楚，但它们仍留在流程里）。

### 7. 打包
- 一道命令出 **`.exe` 安装包**（Inno Setup）；PyInstaller 的 onedir 只是中间产物，
  落在 `build\stage\`，`dist\` 里只有安装包
- 构建自检 `packaging/check_build.py` 查归档模块与数据齐不齐
  （插件式自动发现在打包后最容易**静默失效**——界面能开、功能列表却是空的）

## 已知问题 / 风险

1. **游戏版本更新会让模板 / 坐标 / OCR 匹配串失效**。这类工具天生要跟着版本维护。
   已踩到两次：`阶段放入` 的按钮文案会随状态变、ok-ww 的模板图与 vendored 代码**版本要对齐**。
   → 上游 `vendor/okww` 是**旧快照**；取素材时务必确认与代码版本一致（已写进记忆）。
2. **权限是硬门槛**：鸣潮带 ACE，游戏跑在 High 完整性；本程序必须**以管理员运行**，
   否则 UIPI 会把点击全部丢掉，而且**不报错**。开发态还要把父程序（PyCharm/终端）一起提权。
   现在有启动前预检拦住这种情况并给出可操作提示。
3. **静默失败是这个项目最大的敌人**。已遇到**六类**，全部加了护栏：
   任务被 ok-script 语言门禁静默跳过 / **任务没写进引擎注册表**（09-25 第二次中招，
   同一个坑换了张脸）/ 托盘建不出来 / 点击被 UIPI 吞 / 异常没送到界面 /
   **护栏本身是空转的**（断言看着通过、其实什么都没验到）。
   → 新增任何"可能失败但不该中断"的代码，**失败必须留痕（log）**。
   → 清单类的检查**必须遍历数据**，点名写死会在新增成员时静默失效。
   → 护栏要**抓状态不抓文案**、**走真实路径**、**别拿被测函数算期望**，且每条都要**反证**。
4. **合规**：ok-ww 的 README 自带封号警告（官方把自动挂机列为违规）。自用，但风险摆在这儿。
5. **资料会过期**：角色 / 套装抓的是游戏 3.6 版，出新版本要重跑「资源库更新」。
6. **仍未真机验证的**：Inno Setup 本机没装，**完整打包链路没跑通过一次**
   （验证到「PyInstaller 产物路径正确 + 构建自检通过」为止）。
7. **判定规则是"用户喜好"不是"最优解"**：双爆下限、满值保护、有效词条数的交互
   改过好几轮（09-25 一天内改了两次方向）。改这一块**先读测试里那些"谁压过谁"的用例**——
   它们就是需求规格。


## 关键技术决策

- **分层**：`core/` 不依赖 Qt（所以能命令行单测），`gui/` 只碰 Qt，`tools/` 放实现。
  这条线守住了，测试才好写。
- **资料数据与代码分离**：角色 / 套装放在 `src/core/data/*.json`（不再写死在 .py 里），
  每个文件带 `_source` / `_fetched`，界面顶部也显示出来 —— 让人一眼看到这份资料的
  出处和时效，而不是把第三方整理的内容伪装成权威数据。
- **兼容层**：`gui/compat.py` 把"第三方库名字改了"的风险关在一个文件里，
  图标名和控件类名都走多级降级。
- **存储容错**：配置文件损坏 / 缺字段 / 格式变过（声骸从单条变列表）都不抛异常，
  只跳过能跳的。

## 走过的弯路（都记在 `README.md` 和工作区记忆里）

- `qfluentwidgets.ComboBox` **不显示 item 图标** → 套装下拉是用 `PushButton` + `RoundMenu` 自己拼的。
- `EditableComboBox` 不做候选过滤，回车还会把无匹配内容塞进候选列表 → 子类覆盖。
- `ScrollArea` 的深色底要三件套才能治（`WA_StyledBackground` + 自身样式 + viewport 样式）。
- `MaskDialogBase` 必须有 parent，否则构造就崩。
- 弹框截图要把子窗口先清掉，否则会被画进整窗截图里。
- **弹层 BUG 连环两起**（都是"能弹出来但用不了"）：
  1. 框架菜单是 `Qt.Popup`，会 `grabKeyboard()` → 候选弹出来了但**打不了字**；
     去掉 Popup 后又引入
  2. 点菜单会让菜单窗口激活、输入框失焦，而"失焦即关闭"抢在点击之前把菜单关了 →
     **点了候选没反应**。最终靠 `WindowDoesNotAcceptFocus`（菜单连焦点都不接受）解决。
- **省事的验证方式连续骗过我两次**：用 `setText()` 验输入（绕过键盘通路）、
  直接给菜单子控件发点击（跳过窗口激活）。→ 定成规矩：**验"能不能用"必须复现真实事件链**，
  键盘用 `QTest.keyClicks` + `keyboardGrabber()`，弹层点选先 `setFocus()` 模拟激活再点。
- **QLabel 自动换行的高度在嵌套布局里必然算不准** —— Qt 的 `QBoxLayout` **不传播**
  `heightForWidth`，父布局会把卡片压掉几像素，表现是「最后一行文字被裁掉一半」。
  解法：给 label 固定宽度 + 给卡片 `setFixedHeight(layout().totalSizeHint().height())`。
  这个坑是靠"断言卡片高度 ≥ sizeHint 高度"抓出来的，肉眼只看截图容易当成渲染伪影。

# 第 5 阶段总结（2026-09-22 · 资源库资料化 + 任务系统）

## 这一阶段做了什么

### 1. 鸣潮资源库资料化
- **官方数据源接入**：库街区 wiki 的 `getPage` 接口（POST form，请求头 `wiki_type: 9`，
  `catalogueId=1107`）一次拉全 199 条声骸记录 + 标签树。tagTree 是 **dict** 不是 list，
  套装标签只认「套装」分组下的 34 个子节点（COST / 级别 / 异相都是同级分组，别混）。
- **声骸掉落池补全**：bwiki 的 138 条是官方 181 条的严格子集，并集合并后 34 套 4C/3C/1C 全齐
  （碎梦亡鬼之魇是 1 件套，只有 4C 是对的）。合并一律取并集，任何一边刷新都不冲另一边。
- **资源库页面**：三个分区（角色头像 / 声骸套装 / 声骸图鉴）都套了折叠卡片；
  声骸图鉴按 4C/3C/1C 分组，每行 图标 + 技能说明（来自 bwiki 声骸页解析，138/181，
  43 个新声骸 bwiki 还没建页；库街区详情接口要登录令牌，实测假 token 直接 500）。
- **真图标**：库街区记录自带官方图床 URL，替换占位图的判据是
  "import 占位图脚本重画一张对比字节"——字节一致才覆盖，真图零风险。

### 2. 新分类「数据」+ 鸣潮资源库更新工具
- 新工具分类 `DATA`（数据），主页自动分组。
- 工具面板：打开即后台检查（QThread，3~4 个轻量请求，不写盘）→ 有更新则提示 +
  变更摘要 + 「获取最新数据」点亮 → 点击应用（效果替换 / 掉落池并集 / 新声骸补技能）→
  提示重启生效。核心逻辑在 `src/core/wuwa_update.py`（无 Qt，命令行可单跑）。

### 3. 任务系统（本期主体）
- **侧栏新增「任务」页**（主页 / 配置 / 任务 / 工具 / 资源库，可拖动排序）。
- **任务流程模型**（`src/core/tasks.py`，无 Qt）：流程 = 名字 + 任务类型 + 有序步骤；
  步骤分「工具」和「配置」两种，配置挂到它上面最近的工具下，悬空配置保存时丢弃并提示。

## 安全边界：运行时碰了游戏的什么

（2026-09-22 逐项排查。结论：**不读、也不修改游戏进程内存**。）

| 类别 | 状态 | 证据 |
|---|---|---|
| 进程内存读写 | ❌ 无 | 全项目搜 `ReadProcessMemory` / `WriteProcessMemory` /
`VirtualAllocEx` / `VirtualProtectEx` / `CreateRemoteThread` / `SetThreadContext` /
`MiniDumpWriteDump` / `PROCESS_VM_*` / `PROCESS_ALL_ACCESS` —— **0 命中**。唯一一处
`OpenProcess` 在 `core/game_client.py`，权限是 `PROCESS_QUERY_LIMITED_INFORMATION`
（只够问"这个 pid 的可执行文件叫什么"，拿不到地址空间） |
| 注入 / 钩子 / 驱动 | ❌ 无 | `SetWindowsHookEx` / `LoadLibrary` / `DeviceIoControl` → 0 命中 |
| 内存类依赖 / 夹带二进制 | ❌ 无 | 依赖只有 mss / opencv / onnxruntime / onnxocr / pywin32 / shapely；
仓库里没有任何 `.dll` / `.pyd` / `.exe` |
| 第三方实现 | ❌ 未引用 | ok-ww 只在注释里作为**思路参考**出现，没有 import、没有拷贝其代码 |
| **屏幕像素** | ✅ 读 | `mss` 抓屏（GDI `BitBlt`，源是整屏 DC）→ 交给 OCR 认字（`controller.py`） |
| 窗口元数据 | ✅ 读 | 窗口标题、客户区几何（`controller.py`） |
| 进程信息 | ✅ 读 | 进程名列表 + 目标 exe 文件名，只用于比对（`game_client.py`） |
| **键鼠输入** | ✅ 发真实前台事件 | `mouse_event` / `keybd_event`（`controller.py`）—— 游戏收到的是"真实玩家操作" |
| 游戏文件 | ❌ 不碰 | 项目所有读写都在自己的 `data/` / `assets/` 下，没访问游戏安装目录或 AppData |
| 网络 | ✅ 只访问 wiki | `wiki.biligame.com` + `api.kurobbs.com`（图鉴数据），与游戏进程无关 |

两条要留意（**不是**"读内存"，但属于已知影响面）：

1. 它**靠 OCR 认字**而不是读内存 —— 这正是坐标必须校准的原因；
   （真读内存的作弊工具根本不需要截图和 OCR。）
2. 所有动作都**走游戏自己的 UI**（点按钮 / 按 C 上锁 / 按 Z 弃置），等价于你手点。

   本项目不做这个判断。另外**按 Z 弃置不可逆**（真分解声骸），用之前留意那个开关。

# 第 6 阶段总结（2026-09-23 · 装机版四个问题的修复）

## 一句话现状

把安装包在**另一台电脑**上跑通时暴露的四个问题全部修掉：
① 提权（游戏在管理员权限下，工具不发提权就一点都点不动）；
② 首启动资源库空白（种子数据播种晚于数据模块导入）；
③ 声骸强化只跑一次（「培养」被塞进了每次强化的循环里）；
④ 任务流程没按工具页配的规则筛选（跑的是代码里的默认判定）。

## 1. 启动即以管理员运行（新增 `src/core/elevation.py`）

**病因**：鸣潮带 ACE 反外挂，游戏进程是 **High 完整性级别**；Windows 的 UIPI 禁止
低完整性进程向高完整性窗口注入输入 —— `SetCursorPos` / `mouse_event` 直接失败
（`(0, 'SetCursorPos', 'No error message is available')`），`keybd_event` 则是**静默丢弃**。

**修法**：

- `packaging/mytools.spec` 加 `uac_admin=True` → exe 清单要求 `requireAdministrator`，
  双击就弹 UAC 以管理员启动（实测：不提权启动会直接 `WinError 740 请求的操作需要提升`）；
- 新增 `core/elevation.py`：查自身提权状态 / 目标进程完整性级别（`TokenElevation` /
  `TokenIntegrityLevel`）、`ShellExecuteW("runas")` 一键提权重启、以及把
  `(0, 'SetCursorPos')` 这类报错翻译成**可操作**的提示；
- `controller.GameWindow.verify_input_allowed()`：运行前比一次完整性级别 + 做一次
  无副作用的真实探针（`SetCursorPos(当前坐标)`），不通过就抛 `InputBlocked`，
  不再"开始运行 → 第 1 次强化 → 出错"；
- `bring_to_front()` 改成**返回是否真的置前**并在调用处记警告（它以前静默吞失败，
  正是"探测截到的是 MyTools 自己"的原因）。

## 2. 首启动资源库空白 + 检查结果自相矛盾

**病因**：`main.py` 里 `from src.gui.main_window import MainWindow`（连带导入
`core.game_data`）发生在 `paths.ensure_user_data()` **之前**。首启动时用户数据目录还
不存在，`game_data` 在 import 那一刻把**空数据**快照进内存，之后再拷种子也不会重读。
而「鸣潮资源库更新」读的是**盘上的文件**（那一刻已被拷好）→ 于是它诚实地说"已是最新"。
一个看内存、一个看磁盘，两边看着矛盾。

**修法**：

- `main.py`：`ensure_user_data()` 提到**任何 `src.*` 子模块导入之前**
  （`tests/check_frozen_fixes.py` 会按 AST 断言这个顺序，防止以后又被改回去）；
- `game_data`：公用清单改成**可变容器 + `reload_data()` 就地刷新**
  （别的模块是 `from ... import CHARACTERS` 把名字拿走的，重新赋值模块属性它们看不到）；
  新增 `DATA_VERSION` / `ensure_loaded()`；
- 资源库页 `ensure_loaded()` 兜底 + **按数据版本自动重建**（`rebuild()`），
  所以"获取最新数据"之后**不用重启程序**；
- `check_updates` 说实话：远端一条数据都没拉到时报「没能取到远端数据」而不是
  「已是最新」（以前那等于"什么都没查到却说没事"），本地为空也单独提示；
- 命令行入口 `wuwa_update.main()` 同样先 `ensure_user_data()`。

## 3. 只强化一次就停

**病因**：`_enhance_once()` 每次强化都先点「培养」，而「培养」**只在声骸列表页存在** ——
第 2 次强化时人已经站在强化界面，5 秒超时后抛错退出。

**修法**：拆成 `_enter_enhance_panel()`（每个声骸**一次**，连点「培养」直到它消失）与
`_enhance_one_stage()`（每次强化一次，只做「阶段放入 + 强化并调谐」）。
另外：出错时**尽力按 ESC 把画面收回列表**（否则下次运行直接报"没检测到声骸面板"，
用户得自己按 ESC）；`_back_to_list` 加了 ESC 次数上限（兜底动作不能无限按）；
弹窗匹配从 3 字前缀收紧成完整短语。

## 4. 任务流程没按配置筛选

**病因**：`create_task_runner()` 里硬写 `JudgeConfig()` —— 代码里的默认值。
于是"从任务页跑"和"从工具页点运行"用的**不是同一套规则**，
用户在界面上配的核心属性 / 双爆下限 / 有效词条数全都没生效。

**修法**：

- 新增 `core/tool_settings.py`（用户数据目录下的 `tool_settings.json`，按工具 key 分节，
  临时文件 + `replace` 原子写）与 `echo_enhance/settings.py`（`EchoSettings` ↔ `JudgeConfig`，
  每个字段都容错：手改坏的 / 旧版本的值一律落回默认或夹到合法范围）；
- 工具页**每次改动即存盘**，打开页面时回填；
- `create_task_runner()` / `create_task_prep()` 读这一份，并把实际规则写进日志
  （`判定配置（取自工具页保存的设置）：核心 … / 暴击≥… / 有效词条 ≥…`）。

4. **占位/游离控件截图是空白**：`tool.create_widget(win)` 建出来的页面没进任何布局，

新增第三个工具 **「4C 自动战斗」**：检测到进入战斗后按配置输出（普攻 / 共鸣技能 /

# 第 9 阶段：声骸自动强化改用 ok-ww 引擎（2026-09-23）

## 起因

用户在另一台机器上实测：「**声骸自动强化完全没用**」（同一次测试里 4C 自动战斗是好的）。
要求：**找 ok-ww 抄，只是筛选条件改成我那样（保持筛选条件不变）**。

## 定案：流程整段搬 ok-ww，判定留 MyTools

MyTools 原来自己写了一套点击/OCR（`controller.py` / `reader.py` / `prepare.py` /
`runner.py`，共 ~1300 行）。同期的「4C 自动战斗」走 vendored ok-ww 引擎是跑通的 ——
同一件事有两套实现，那就只留跑得通的那套。

* **搬**：整个 `okww.task.EnhanceEchoTask` 的流程（培养 → 阶段放入 → 强化并调谐 →
  关弹窗 → OCR 词条 → `Z` 弃置 / `C` 上锁 → 找下一个 0 级声骸），
  坐标 / 模板 / OCR / 后台按键全是 ok-ww 原样。
* **不搬**：ok-ww 自己的筛选规则（必须有双爆 / 双爆总计 / 首条双爆 /
  第一条必须为有效词条 …），换成 `stats.judge()` 那套
  （核心属性 / 可选属性 / 双爆各自下限 / 满值保护 / 有效词条数）。

## 关键实现：三态怎么映射回 ok-ww 的布尔

ok-ww 的判定入口只有一个方法，返回布尔：

```python
check_echo_stats(properties, values) -> bool     # True=继续强化，False=弃置
```

于是**只 override 这一个方法**就够，主循环一行都不用改：

| `judge()` 的动作 | 返回 | ok-ww 侧的落点 |
|---|---|---|
| `discard` | `False` | 按 `Z` 弃置 |
| `continue` | `True` | 继续强化 |
| `lock` | `True` | 主循环里 `len(properties) >= 5` 时上锁 |

`lock` 映射成 `True` 不是偷懒：MyTools 的 `lock` **只在词条满 5 条时**才出现，
而 ok-ww 恰好就在那个时刻上锁 —— 两条路的落点一致。
「满值保护」返回的是 `continue`（继续强化到满级再上锁），语义也正好对得上。

| 文件 | 改动 |

## 两处"不照抄"的地方（有意为之）

1. **配对前先剔掉认不出的属性名**。ok-ww 只过滤了「辅音」，剩下任何 OCR 噪声都会

   `judge()` 本来就只认标准词条，提前剔掉是纯收益。

另外把 ok-ww 的 `Pause after Success` 默认改成 `False`：

# 第 7 阶段：引擎随程序启动 + 战斗报告（2026-09-24）

## 1. ok-ww 引擎改为「启动应用就默认启动」

  `QTimer.singleShot(AUTOSTART_DELAY_MS, _autostart_okww_engine)`

- `okww_boot.autostart_engine()` 只做 `get_host().boot()`，**吞掉异常只记日志** ——

- 改了行为就把 6 处已经变成假话的说明一起改了（宿主类文档、4C 页模块文档 /
  卡片提示 / 三条状态文案、`__init__.py`、`echo_enhance/settings.py`、README）。

## 2. 战斗报告（做在 4C 页上，边跑边刷新）

**先纠正一个假设**：ok-ww **没有**报告界面（全仓搜 `战斗报告|battle_report|BattleReport`
零命中，`stats` 的命中全是 `cv2.connectedComponentsWithStats` 和声骸词条判定）。
**但它确实在统计** —— 数字都在任务的 `self.info` 里。所以正确做法是**读它的现成数据**：

| 报告字段 | ok-ww 现成来源 | 我们做了什么 |
|---|---|---|
| 战斗次数 | `info['Combat Count']`（`combat_once()` 里 +1） | 取差值 |
| 声骸数量 | `info['Echo Count']`（`incr_drop()` 里 +1） | 取差值 |
| 使用队伍 | `task.chars` | 英文类名 → `i18n/zh_CN/ok.po` 转中文 → 对 MyTools 头像 |
| 战斗声骸 | `task.aim_boss`，认不出则 `config['Boss']` | 认不出标「未识别」 |
| 时长 | —— | 宿主掐表，停止时冻结 |

★ **一个关键取舍：全部靠"读"，一行 ok-ww 执行逻辑都没改。**
  本来准备给 `FarmEchoTask` 写子类加战斗计数器（像声骸强化那样），结果读代码时发现
  `BaseCombatTask.combat_once()` 里**已经有** `self.info['Combat Count'] += 1` ——
  于是子类完全不需要，实现量小了一大截，也不给 ok-ww 升级添麻烦。

★ **必须取差值**：`info` 是任务 `__init__` 里建的空 dict，**同一进程内跨次运行会累加**
  （不是每次清零）。而需求是"本次运行从开始到停止"，所以宿主在 `start_task` 里
  **开跑前快照基线**，报告显示 `当前 − 基线`；并处理了"万一被重置"的边界（当前 < 基线时

## 第 8 阶段：修「声骸自动强化完全没用」（2026-09-24）

用户在另一台机器实测：**4C 自动战斗正常，声骸自动强化"完全没用"**。这次没有靠猜 ——
把 ok-ww 引擎真起了一次、把注册结果数出来，两个根因都是**静默失败**：

### 根因 ①：任务根本没注册（头号原因）

ok-script 的 `task_manager.init_tasks()`：

```python
if len(task.supported_languages) == 0 or locale_name in task.supported_languages:
    tasks.append(task)      # ← 不满足就静默不注册
```

宿主是无 GUI 的（`resolve_ui_config(None) → headless`），`init_app_config()` 拿不到
ok-ww GUI 里那个「语言」设置，`app.locale` 实测就是 qfluentwidgets 的默认值 **`en_US`**；
而 ok-ww 的 `EnhanceEchoTask` 声明了 `supported_languages = ["zh_CN", "zh_TW"]` ——
子类推承门禁 → **任务进不了引擎** → 点「运行」只得到「找不到任务」。
（同类地，ok-ww 自己的 `ChangeEchoTask` 也被这条门禁吃掉了。）

实测证据（同一进程、同一语言）：

```text
修复前：注册的 onetime_tasks = MyToolsFarmEchoTask、MergeEchoTask      ← 少了强化任务
        find_task('声骸自动强化') -> None
修复后：注册 = …、MyToolsEnhanceEchoTask、…                              ← 在
        [PASS] 声骸自动强化 -> MyToolsEnhanceEchoTask
```

`FarmEchoTask` 之所以没事，只是因为**它压根没声明** `supported_languages`。

**修法**：子类里 `self.supported_languages = []`（清空 = 永远注册）。宿主场景里"引擎语言"
这个代理量毫无意义：本工具就是给中文游戏用的，ok-ww 的 OCR 匹配串（`'培养'`、`'阶段放入'`…）
本来就是中文字面量。`run()` 里另加一道检查，语言不是 zh 开头就明确告警。

### 根因 ②：判定规则自相矛盾

`valid_stats = 核心属性 ∪ 可选属性`，而双爆被强制进核心 → 集合最少 2 条；
声骸的 5 个孔位里**每种词条只会出现一次** → `valid_count ≤ 2`。而界面默认要求 **≥3** ——
永远达不到 → **每个声骸都在满级那一刻被判弃置**。这个问题会在修好 ① 之后立刻接棒，
而且比 ① 更隐蔽（表面上"在跑"，实际全丢）。

**修法**：`JudgeConfig.effective_min_valid_count` 把下限夹到 `len(valid_stats)`，
`criterion_warning()` 给一句人话，页面卡片里当场显示、运行时再弹一次 InfoBar。

### 顺带补的两件"可诊断性"

- **弃置原因统计**：`check_echo_stats` 按 `DISCARD_CODES`（core/crit/valid）计数，
  结束时的信息栏显示「已判 N 次，弃置 M 个（原因：双爆不达标 12、有效词条不足 3）」——
  规则太严还是词条读错了，一眼分清。
- **启动失败不再静默**：「引擎就绪后才开任务」这条路以前只写日志、页面什么都不显示，
  用户看到的就是"点了没反应"。现在 `OkwwHost.take_start_error()` 会让页面弹一次 InfoBar；
  「任务没注册」的报错也换成了带诊断的版本（列出已注册任务 + 常见原因）。

### 新增的回归网

- `tests/check_okww_registration.py`：**真起一次引擎**，断言 `TASKS` 里每个任务都注册了。
  这条检查就是为了防止"静默消失"再次发生 —— 光读代码看不出来。
- `tests/check_echo_page_gui.py`：断言配置矛盾时页面出现告警、勾了可选属性后消失。
- 新增 13 条单测（判定钳制 / 弃置码 / 语言门禁 / 统计格式），全量 **316 全绿**。

### 教训

1. **"没反应"要先数事实，别先改代码**：把引擎起起来、把注册列表打出来，比读一百行源码快。
2. **框架的"静默跳过"是最贵的一类 bug**：页面上一切正常，日志里只有一行"找不到任务"。
   只要有这种机制，就该配一条"真起一次、数一遍"的检查。
3. **判定规则要显式检查"是否可满足"**：一个数学上永远达不到的条件，等于把功能整体关掉。

### 后续（同日）：把「有效词条数」与核心属性联动

用户提出：**核心属性有几条，有效词条默认最低就几条且不可减少**，并提示这一点。
这正好从根上消掉了根因 ②：

* `settings.valid_count_range(core, optional)` → `(low, high)`，其中
  `low = max(2, len(core))`、`high = min(5, len(core ∪ optional))`；
* **收敛点只有一处**：`EchoSettings.__post_init__` 把 `min_valid_count` 夹进这个范围。
  界面、磁盘（`from_dict`）、代码三条路都经过它，所以"凑不出来的条件"在模型层就不存在了；
* 界面用它设加减框的范围 + 卡片里一行实时提示（`_sync_valid_count()`），
  `NumberStepper` 新增 `set_range(min, max, emit=)`（`emit=False` 防递归）。

副作用要记住：`DEFAULT_VALID_COUNT` 现在等于 `len(DEFAULT_CORE)`（=2）。
`describe()` 里那句"已达不到 → 已按 ≥N 执行"随之删掉（不再可能发生）；
引擎侧 `JudgeConfig.criterion_warning()` 保留，兜底"直接构造 JudgeConfig"的调用方。

### 联动补完 + 一个我自己造成的事故（同日）

用户报两件事：(a) 核心只有双爆 2 条时，有效词条数应当就是 2；(b) 减少核心属性后，
有效词条数没有跟着降。

**(b) 是真缺陷**：原来的实现只把值**夹进**范围，核心变小只降下限、不动当前值。
现在 `_sync_valid_count(follow_core=True)` 在核心属性变化时把值**带回核心条数**
（`NumberStepper.set_value(low, emit=False)`；`_on_core_changed` 里先跟随再存盘），
上限仍随「有效词条集合」走；卡片说明里补上了这条契约。

**(a) 不是逻辑问题，是我把配置写脏了**：`tests/check_echo_page_gui.py` 切换复选框 /
加减框会触发 `_save_settings()`，而它**没做持久化隔离**，于是把
`optional_stats: [攻击百分比, 共鸣效率]` 与 `min_valid_count: 4` 写进了项目里的
`data/tool_settings.json`。而「可选属性」卡片**默认收起** —— 界面上根本看不出那两条
还勾着，用户只看到"核心 2 条、有效词条却不是 2"。`git diff` 是决定性证据：
基线里根本没有 `echo_enhance` 这一段，整块都是新加的。

修法：脚本改成 `tool_settings.settings_file = lambda: tmp/"tool_settings.json"`
（与 `check_settings_gui.py` 同一姿势），并在结尾**断言真实文件一个字节没变**；
被写脏的配置用 `git checkout --` 还原（diff 证明只多了那一块，零损失）。

**连带查出**：`check_settings_gui.py` 有 3 处断言还停在旧语义（默认 3、`set_value(5)`），
而它**不在 unittest 套件里**，所以"319 全绿"完全看不出来。已更新（先勾可选属性再设值，
否则会被夹到 2）。教训：**GUI 检查脚本要当一份清单逐个跑，别只信套件。**

**GUI 检查脚本的硬规矩**：任何会构造页面 / 切换控件的脚本，**必须在构造页面之前**把
持久化路径指到临时目录（`tool_settings.settings_file`），并在结尾断言真实文件哈希未变。

# 第 11 阶段：真机联调周 —— 「跑起来之后才暴露的问题」（2026-09-25 / 09-26）

## 一句话

## 逐项

### 1. 环境与依赖（09-25）
requirements.txt **漏了 `ok-script`**（真正必需的依赖，只在文档/许可/打包配置里提过）。

第二条单独装 ok-script 且必须带依赖解析（把 pywin32 从 312 降到 311）。
另修 `tests/test_okww_vendor.py` 里一个 Python 3.13 专属 API（venv 是 3.12）。

### 2. 游戏素材取回（09-25）
- bwiki 素材 222 张（58 头像 + 34 套装 + 130 声骸图标）
- **ok-ww 上游资产 49 个**（48 张模板图 + `echo.onnx` 37.9MB，被 .gitignore 排除）
- 踩坑：本机 `curl` 对 github 系域名一律「200 但 0 字节」，**必须用 urllib**；
  `raw.githubusercontent.com` 直接 ConnectionReset；`gh-proxy.com` 最快。
  按实测速度排通道 + 8 线程并发后，**2.5 小时 → 23 秒**。

### 3. 「声骸自动强化完全没效果」的真机三层原因（09-25）
三层**互相掩盖**，一层层剥：

| 层 | 现象 | 根因 |
|---|---|---|
| ① 权限 | 日志刷 `PostMessage error … 拒绝访问` | 游戏是 **High 完整性**（ACE），工具是 Medium → **UIPI 丢点击** |
| ② 游戏设置 | 修完①仍报「阶段放入!」 | 「阶段放入」**没在游戏里开**（README 写明的前置条件） |
| ③ 报错误导 | 界面显示「请确认停在背包→声骸界面」 | ok-ww 的异常**只进日志没进界面**，界面显示的是通用文案 |

修法：启动前**权限预检**（拦在拉引擎之前）+ `format_result_report` 支持
`failed_reason`（有真实原因就优先显示）。

### 4. 判定顺序与规则（09-25，一天内改了两轮方向）
- 第一轮理解错：把「双爆下限」提到「满值保护」前面 → 用户说不对
- **真因**：双爆下限的实现要求「暴击与爆伤**都出现**才判」，
  理由是"另一项还有孔位可以博"——**这个理由是错的**：
  声骸每种副词条**只会出现一次**，已经读出来的暴击 6.3 就是这个声骸的最终值，
  后面的孔位再多也补不回来。于是低值声骸会一直被强化下去。
- 修法：改成**任一已出现项低于下限就弃置**；满值保护回到**最高优先**。
- 顺带修掉一个**原本就存在**的 bug：reason 里的 `<` 是 Windows 文件名非法字符。

### 5. 托盘 / 后台运行 / 关闭确认（09-26）
三个需求：点运行后自动退到后台 + 切游戏到前台；关闭时问「隐藏到托盘 / 直接退出」；
有任务在跑时**点名是哪个**在跑。

**踩了两个坑**：
- `qfluentwidgets.MessageBox` **没有 `clickedButton()`**，而 `exec()` 对

### 8. 声骸强化「跑到一半自动停止」（09-26）
日志显示跑了 **42 次判定、弃置 9 个**之后中断，报「强化设置需要开启阶段放入!」。

**一眼定案靠的是工具自己存的失败截图**：材料区按钮写的是 **「清 除」**、
材料槽 2/50 有东西、声骸还停在 +0。

**根因**：ok-ww 的 `find_add_mat()` 只认「阶段放入」，而那个按钮的**文案随状态变**：
- 材料槽空着 → 「阶段放入」
- 材料已在里面 → **「清 除」**

只要有一轮「强化并调谐」没把材料消耗掉（点击被界面过渡吞掉，偶发），
下一轮就找不到「阶段放入」→ 空等 5 秒 → **抛异常，整个任务当场结束**，
报的错还跟真实状态正好相反。

**修法**（`okww_task.py` 覆盖三处）：`find_add_mat()` 认出「清 除」= 材料已就绪，
返回一个**哨兵**（**只报告一次**，否则外层 `break` 不出去、每个声骸白等 5 秒）；
`click()` 拦掉哨兵（**它代表「清 除」，真点会把材料撤掉**）；补一行日志让恢复可见。

> 中途先用**动作计数**否掉了错误假设：`强化并调谐 42 / 调谐成功 42` 基本对齐
> → 说明不是"点击普遍被吞"，只是个别轮次。省了一次大改。

# 第 12 阶段：新增声骸批量调频工具（2026-09-26）

## 一句话

第四个工具：**批量把声骸主属性改成指定属性**（游戏里的「调频」＝详情页「数据重构」）。
设计见 `docs/声骸批量调频工具设计.md`，代码在 `src/tools/game/echo_change/`。

## 为什么这次**整段重写**了 ok-ww 的 `run()`

上一个工具（声骸强化）的原则是"流程整段用 ok-ww 的、只覆盖判定"。
**这个不行** —— 要改的三处全在 `run()` 函数体内部，没有可覆盖的钩子：

1. **属性名用子串比较**（`"攻击" in "攻击百分比"` 是 **True**）——
   会把"明明该改的"声骸误判成"已经相同"，然后**抛异常中断整个任务**。
   这是实现阶段才发现的，比"已经相同"本身**更常见**。
2. **「目标属性相同」是 `raise`** —— 而过滤器筛出的一批里必然混着几个已经是目标属性的。
3. **五处 `raise_if_not_found=True`** —— UI 过渡期 OCR 抓空一个就炸整局。

## 三个设计取舍

- **精确比较**（归一化后相等），顺带吃掉 OCR 噪声（前缀 `+` / 空白 / `主属性` 字样 / 全角 `％`）
- **「已经是目标属性」→ 记一次跳过 → 停下并提示收紧过滤条件**。
  ⚠ 设计时想的是"跳过并**继续**"，实现时发现**做不到**：ok-ww 的循环永远处理列表里
  **第一个**声骸，跳过之后下一轮还是它 → **死循环**。停下并给可操作说明是更诚实的做法。
- **单步失败 → 有限重试 → 记成"这个声骸失败" → 回列表 → 下一个**；
  连续失败 3 个才整体停（否则会卡在一个处理不了的声骸上无限重试）

## 验证

# 第 15 阶段：配置页改名「角色声骸搭配」→「角色声骸筛选配置」（2026-09-26）

## 改了什么

同一个名字原先**散在 3 处**（都是直接写的字面量）：

| 位置 | 改动 |
|---|---|
| 配置页小节标题 `_section("角色声骸搭配")` | → `_section(TYPE_LOADOUT)` |
| 顶部计数文案 `… 条角色声骸搭配` | → 用 `TYPE_LOADOUT` |

## 为什么可以放心改字面量

`TYPE_LOADOUT` / `TYPE_ECHO_PROFILE` **只是界面字面量**，不参与持久化：

- 两类配置分别存在 `loadouts.json` / `echo_profiles.json`，里面**没有** `type` 字段；
- 类型比较走 `chosen_type()` → `currentText()`，和常量同源，改了一起变；
- 全库 grep 无测试引用该字符串。

→ **老用户的数据不受影响**，不需要迁移。

## 新增护栏（`check_echo_page_gui`，60 → 64 项）

断言"配置页小标题 / 计数文案 / 类型下拉**用的是常量**"，而不是钉死字面量

## 二、四条需求的落点

### ① 名字改成角色下拉（不能自由输入）

`EchoProfileDialog` 的 `LineEdit` 换成 `FilterComboBox`（可打拼音筛）+ **保存时校验**。

* 必须**精确命中**数据集里的一个角色；
* 该角色不能已被别的配置占用。

> 为什么"候选里剔掉"不够：`FilterComboBox` 是**可输入**的，用户能把候选筛空、
> 直接敲一个字就点保存。所以保存时必须再校一次。

### ② 一个角色只能一条（两类都改）

* `EchoProfileStore.occupied_characters()`；
* `LoadoutStore.occupied_characters()` / `has_character()`（新增）；
* 两边的弹框都把已占用的角色从候选里剔掉 + 保存前校验。

> ⚠ **`LoadoutStore.add()` 故意不硬拦**：loadout 主键是 `id` 不是角色名，
> 而且**老文件里可能已经有同一角色的多条**（旧版明确允许），那些必须照常读得出来。
> 所以"一角色一条"是**界面层的规则**，不是存储层的不变量 ——
> 这点和 `EchoProfileStore` 不同（那边主键本来就是名字，天然拒绝重名）。
> 这个不对称是**有意的**，写进了 `occupied_characters()` 的 docstring。

### ③ 「默认」那条：不再种子 + 清掉已有的

* 删掉 `ensure_default()`，换成 `purge_legacy_default()`；

# 第 19 阶段：列表里的名字加类型后缀（2026-09-26 晚）

用户截图：箭头指着「角色声骸强化」那条配置下面的名字「绯雪」，批注

> 改成如果是角色声骸强化，保存时，默认加上-声骸强化，如绯雪-声骸强化，
> 如果是角色声骸筛选，默认加上-声骸筛选

## 一、后缀只加在**显示**上，存盘仍是纯角色名

新增两个共用函数（放在 `echo_profile_ui`，`config_interface` 复用）：

```python
type_suffix("角色声骸强化")             # -> "-声骸强化"
config_display_name("角色声骸强化", "绯雪")  # -> "绯雪-声骸强化"
```

`type_suffix` 的做法是**去掉开头的「角色」** —— 这样以后类型名再改
（用户已经改过一次：`角色声骸筛选配置` → `角色声骸筛选`），后缀自动跟着变。

**⚠ 为什么不去改存盘里的名字**（`EchoProfile.name` / `Loadout.character` 仍是「绯雪」）：

1. **行上的头像是拿名字去 `find_character()` 查的** —— 带后缀就查不到，

2. 「角色」下拉里必须显示**纯角色名**，否则编辑时回填不回去；
3. 类型名是**显示常量**，烤进存盘数据会让老数据带上过期后缀，每次改名都要迁移。

谁用到后缀：列表行名 / 编辑·查看弹框标题 / 删除确认文案。

# 第 21 阶段：编排区支持「在中间自由插入」（2026-09-26 晚）

## 一、实测先确认"现在到底行不行"

构造一个 `QDropEvent`（拿组件区某项的 mime）打到编排区的第 0、1 项之间：

```
塞 3 项后：        ['[开始] 开始', '[工具] 声骸自动强化', '[配置] 绯雪-声骸强化']
拖到 0、1 项之间：  […同上…, '[工具] 4C 自动战斗']      ← 追加到末尾了
```

→ **Qt 在 IconMode 下不按落点插，一律追加到末尾**。这就是用户说的问题。

## 二、实现：自己算插入位置

`FlowListWidget` 加三件事：

1. `insert_index_at(pos)` —— 落点在某一项**左半边**就插到它前面、右半边插到后面；
   不在任何项上时按 x 跟每项中心比，都没有就排到最后。
2. `dropEvent` 接管：
   * **组件区拖进来的** → 在落点处插入一份新的（**复制**，组件区那份留着）；
   * **编排区内部拖动** → 先把选中的拿走、再插到落点（"拖到哪儿排到哪儿"）。
3. `dragMoveEvent` + `paintEvent` 画一条**蓝色竖线**指示"会插在哪" ——
   没有它用户根本看不出来能插在中间。

## 三、★ 两个差点踩爆的坑

### 坑 1：`dropMimeData(row)` 在 `row < count` 时是**覆盖**，不是插入

第一版直接 `model().dropMimeData(mime, Copy, index, 0, QModelIndex())` ——
**塞 3 项只剩 2 项**，原来那一项被顶掉了。逐行实测：

```
row=0（count=0）→ 1 项   ✔ 插入
row=1（count=1）→ 2 项   ✔ 插入（row == count）
row=1（count=2）→ 2 项   ✗ **覆盖**（Qt 的 decodeData 先 setData，超出末尾才 insertRows）
row=2（count=2）→ 3 项   ✔ 插入
```

→ 正确做法：**先自己 `insertItem(index, "")` 开一个空行**，再把 mime 灌进这一行
（role 数据、含 `UserRole` 里那个 dict，都会原样写进去 —— 实测确认）。

### 坑 2：内部拖动**不能用 MoveAction 收尾**

Qt 的 `QAbstractItemView::startDrag` 里有这么一句：

```cpp
if (drag->exec(supportedActions, defaultDropAction) == Qt::MoveAction)
    d->clearOrRemove();          // 把源行删掉
```

而搬移是我们**自己**做的（takeItem + insertItem），Qt 再删一次就**删第二次**
（数据丢失）。两个分支都改成用 `CopyAction` 收尾（外部拖进来本来就该是复制）。

> 内部搬移那段抽成了 `move_selected_to(index)` ——
> **为的是能单测**（下标要减去"原本排在它前面、已经被拿走"的那几项，
> 这是最容易错位的地方）。顺带：落点下标是"搬之前"的语义。

## 四、护栏（`check_task_editor_gui` 22 → 31 项）

* 拖到中间 → **插在中间**（不是追加）
* 插入**没顶掉**原来那一项（数量 = 4）
* **连插两次**位置都对
* 从组件区拖进来是**复制**（组件区不减项）
* `insert_index_at` 的左半边 / 右半边 / 末尾三种边界
* 内部排序：拖到末尾就排到最后

**反证**：把 `dropEvent` 换回 `super().dropEvent(event)`（Qt 默认）→ 立刻红 2 条，
报错里直接能看出 `4C 自动战斗` 被追加到了末尾：

```

     ['[开始] 开始', '[工具] 声骸自动强化', '[配置] 绯雪-声骸强化', '[工具] 4C 自动战斗']
```

## 一、这个 bug 本身 30 秒能修，真正害人的是它被"洗白"了

`_wrap_input_error` 原来**无条件**把任何异常翻译成"权限不足"，于是上面那句
`TypeError` 变成了：

```
权限不足：游戏以管理员身份运行，本工具权限比它低…
（本工具 管理员级）
本工具已经是管理员权限，仍然被拦 —— 这多半是游戏反外挂（ACE）拦下了合成输入，
此时自动化点击这条路走不通。
```

**用户照着这句话去做的每一步都是白费的**：重新提权（已经提了）、查反外挂、
怀疑输入方式。而日志里明明写着 `takes at most 4 arguments (5 given)` ——
**最有用的那句被埋在最没用的那句下面**。

这是第 28 阶段那个「误导性报错」的**同一个病**换了个位置复发：
上次是"坐标可能不对"，这次是"多半是反外挂"。**归因错了，修复方向就全错。**

### 修法

`_wrap_input_error` 只在异常**真的像权限/系统拒绝**时才包装成 `InputBlocked`；
代码自身的错误（`_PROGRAMMING_ERRORS` = TypeError / AttributeError / ValueError /
KeyError / IndexError / NameError）**原样暴露**：

```
按键 B 失败 —— 这是**代码/环境问题，不是权限问题**：
keybd_event() takes at most 4 arguments (5 given)
```

⚠ `RuntimeError` **不能**放进 `_PROGRAMMING_ERRORS` —— `InputBlocked` 就是它的子类。

顺带全扫了一遍同类归因点：`admin_hint` 共 3 个调用处，另两处
（`controller.verify_input_allowed`、`okww_boot._permission_reason`）都是
**真去比完整性级别**、以 `own < target` 为前提的，没有这个问题。

## 二、护栏：参数个数的事实来源是 pywin32，**不是微软官方签名**

写护栏时先实测了一遍，结果很反直觉 —— 官方 C 签名和 pywin32 的包装**不一致**：

| API | 官方 C 签名 | pywin32 实际（本机实测） |
|---|---|---|
| `keybd_event` | 4 | 最多 4（5 个 → TypeError） |
| `mouse_event` | 5 | **4、5 都接受**（宽松，"必须 5"当护栏会误报） |
| `SetCursorPos` | 2（x, y） | **正好 1**（要传元组；传 2 个**反而** TypeError） |

`SetCursorPos` 那行是个陷阱：项目里 3 处 `SetCursorPos((x, y))` 是**对的**，
照官方签名写成"必须 2 个"会把 3 处正确代码判成 FAIL。

所以护栏不用手写常量表，而是**规则取自 API 本身**：

* `tests/test_input_api.py`（**11 条**）
  - **归因**：TypeError / AttributeError 不许是 `InputBlocked`，且原文要留着；
    `PermissionError(5, …)` 和 `(0, 'SetCursorPos', …)` **仍然**要报权限（别矫枉过正）；
    `RuntimeError` 不在归因表里（护住 `InputBlocked` 这个子类）
  - **AST 扫源码**：`keybd_event` ≤ 4、`SetCursorPos` == 1、不许出现 `f(*args)` 形式
  - **自校验**：真调一次 `keybd_event(0,0,0,0,0)` 确认会 TypeError
    （参数绑定阶段就抛，**没执行到系统调用**，无副作用）；
    真调 `SetCursorPos(0, 0)` 确认 pywin32 那头是**拒绝 2 个参数**的

### 反证（5 条，全部命中）

| 改坏什么 | 哪条红 |
|---|---|
| `keybd_event` 改回 5 个参数（还原事故现场） | `test_keybd_event_within_arity` |
| 去掉"代码错误不背锅"分支（还原旧的无条件包装） | `test_typeerror_...` + `test_attribute_...`（2 条） |
| `SetCursorPos` 改成照官方签名的 2 个位置参数 | `test_set_cursor_pos_exact_arity` |
| 引入一处 `f(*args)` 形式的 win32 调用 | `test_no_starred_win32_calls` |
| 扫描目录指向空目录 | **只有** `test_at_least_one_call_scanned` |

最后那条最有价值：扫不到调用点时，两条 arity 检查**静默变绿（空转）**，
只有前置断言亮红 —— 这正是前置断言存在的理由。

`_notify_task_started()`；而 `OkwwTaskRunner.run()` 的第一条日志没出现 ⇒
`start_task` 没返回 ⇒ **只能卡在它**。

回调是 `MainWindow.go_background_to_game()` —— 里面 `hide()` /
`processEvents()` / `QTimer.singleShot()` **只能在 Qt 主线程做**，
而它是被 **FlowRunThread（工作线程）** 调用的。

> ⚠ 上一轮我把它列进猜测又用**最小复现否掉了**（那次主线程空闲、事件队列空，
> 当然不卡）。**"最小复现没复现出来" ≠ "不是它"。** 这次靠日志的**排他性**钉死。

## 二、修（两层）

1. **界面侧**：`MainWindow` 加 `task_started = Signal()`，
   `__init__` 里连到 `go_background_to_game`，监听回调只 `emit`。
   Qt 跨线程 `emit` 安全，槽自动排到**主线程**执行。
2. **宿主侧**：`_notify_task_started` 把喊话丢到独立守护线程。
   "通知界面"本就只是顺带说一声，**任何监听者卡住都不该拖住任务启动**。
