## 二、最终实测结果（走生产代码）

```
冷启动（全库搜，无连续性）
  ±2 命中 94.8%    ±5 命中 95.8%    余量中位 0.047

顺序模式（真实工况）
  定位跑飞 0    误纠偏 0    可用率 71%    dx 误差中位 1.8px

闭环残差（按 -dx 撤销后）
  中位 0.171px    最大 0.478px

闭环仿真（σ=12px/步压力测试）
  误纠偏 0    偏航有界（峰值 71px）    推进 44 参考帧

跨视频（库建自 p1.mp4，9.6 分钟；查询/干扰用 p4.mp4，27.3 分钟）
  泛化：p1 的**留出帧** ±2 命中 85.9%
  拒识：拿 p4 的帧查 p1 的库 → 只有 2% 高可信（**不会自信地认错**）
```

> ⚠ **跨视频这条最重要**。在同一个视频上测只说明"记得住"；
> 跨视频测的是"泛化"和"拒识"。拒识失败 = 机器会朝完全错误的方向走，
> 所以判据是「**不许自信地认错**」而不是「必须 0 误报」——
> 描述子总有偶然相似，允许偶尔报个位置，但**高可信**的必须极少。

## 三、★★ 三个关键结论

### 3.1 只靠闸门堵不住「认错地方」

交叉表（155 样本）：

```
                  定位对    定位错
  过闸门            110       12     ← ★ 危险格
  被拦下              9       24
```

最恶劣一例：

```
anchor#3106  S=60  定位到 #2374   peak=0.057   dx=+0.2
```

`#3106` 与 `#2374` 差 **1272 个参考帧 ≈ 10.6 分钟** —— 一帧之内从视频
10 分钟处"跳"到 21 分钟处，物理上不可能。但 `peak=0.057` 越过了 0.05
的闸门，于是它给出的 `dx=+0.2`（真值 +60）**会被采信** ——
机器朝完全错误的方向纠偏。

**根因**：闸门量的是"两张图**能不能对齐**"，不是"是不是**同一个地方**"。
开放世界到处是相似的海岸线/草地，别处的帧当然也能对得很齐。

**解法 —— 三层把关，各管一件事**：

```
连续性（窗口 ±30）  →  位置**合不合理**
独特性余量          →  地方**认没认准**
相位相关 peak       →  这一帧**对不对得齐**
```

效果：

```
配置              危险格   误纠偏   定位跑飞   可用率
只用闸门             5       5       23%      72%
连续性 + 余量        0       0        0%      92%   ← 更好，而且更安全
```

> 注意可用率反而**升了**：拦住错匹配的同时，也让正确的小偏离更容易被接受。

### 3.2 「先对齐再打分」—— 大偏航能启动的关键

相关型描述子**不是平移不变的**。画面横移 80px 时，**真值那一帧**的
相似度从 0.99 掉到 0.93，而"别处"的帧本来就在 0.92 —— 余量被压没。

| 偏航 | 原始相似度选最佳 | 先对齐再打分 |
|---|---|---|
| 0px | 90% | **100%** |
| 20px | 82% | **100%** |
| 45px | 67% | **100%** |
| 60px | 44% | **100%** |
| 80px | **18%** | **100%** |

**做法**：取原始相似度 top-5 候选 → 各做一次相位相关 → **按 shift 把查询
画面搬回去** → 再算相似度 → 谁"搬回去之后"最像，谁才是真位置。

搬回去之后是**平移不变**的：真值那一帧回到 ~0.97，别处依然不像，
余量 0.015 → 0.064（翻 4 倍）。

**没有它，45px 起步的回路永远启动不了** —— 鸡生蛋：要纠偏得先量准，
要量准得先不偏。

### 3.3 自动标定（不靠人眼估）

`PX_PER_TURN_SEC`（秒/像素）取决于游戏灵敏度 / DPI / FOV，猜不出来。
没标定就跑 = 照错的换算转 = **唯一会"乱走"的情形**。

既然**测偏移**已经做到亚像素精度（闭环残差最大 0.478px），直接拿它量：

```
① 拍一帧 → 按 d 键 H 秒 → 再拍一帧
② 相位相关量出横移多少像素
③ 几个 H 各做一次（0.10 / 0.20 / 0.35s）→ 过原点最小二乘
     秒/像素 = Σ(h·px) / Σ(px²)
```

单测用**无噪声假世界**验证：能恢复到真值 **±5%**（0.0012 → 0.0012）。

**失败时返回 0.0**（不是瞎猜一个数）—— 画面没动 / 对着 UI 时明确
判定失败，让调用方拒绝运行。

### 3.4 死区 = 永久死锁

原来有 `align_px=40` / `correct_px=60` 两个阈值，于是 40~60px 成了
"谁也不管"的区间：

```
不前进（超了 align）
不纠偏（没超 correct）
只 WAIT —— 而 WAIT **不改变任何状态**
→ 下一帧还是 WAIT → 永久死锁
```

**仿真实测：起始偏航 41px 时 600 帧全 WAIT、0 次推进。**
而 41px 是很容易落进去的区间。

**修复**：**删掉 `correct_px` 字段** —— 结构上不给死区留位置。
只留一个阈值：超了就纠、没超就前进。
0~200px 逐点扫，卡死点 **0** 个。

## 四、⚠ 我犯的三次同款错误（符号）

符号搞反了**三次**：原型脚本、闭环仿真、诊断脚本各一次。
每次的表现都是"**残差恰好是初始偏离的 2 倍**"或"数值发散到 10^12"。

约定由 `diag_sign.py` 实测钉死：

```
注入 +S 右移          →  dx ≈ +S
对当前画面施加 -dx    →  残差 0.00px    ← 正确
对当前画面施加 +dx    →  残差 = 2S      ← 正反馈（发散）
```

**撤销 = 对当前画面施加 `-dx`。**

> 以后碰这个符号：**先跑 `diag_sign.py`，不要靠推理。**
> 三次推理三次错，实测一次就对。

## 五、其他实测坑

| 坑 | 现象 | 正解 |
|---|---|---|
| **源视频不在** | 什么都认不出来、返回 None **且不报错** | 库只存描述子；对齐要回源视频 seek 取原图。视频不能动 |
| 建库/查询用同一份图 | "100% 命中"的假结论 | 建库 `degrade=""`，查询 `degrade="hard"` |
| `cap.set()` 抽帧 | 3280 帧要 137 秒 | **顺序读**只要 73 秒（快一倍） |
| 仿真步长太粗 | 刚锁上就跟丢 | 每步 0.2 参考帧（真实迭代 ~10 次/秒） |
| 把"位置跳了"当跟丢 | 误判 | 画面**在库里**跳了 → 该找到它；**不在库里**才是跟丢 |
| UI 区域当特征 | 相似度掉到 0.87 以下 | 遮罩挖掉（血条/CD/小地图每帧都在变） |

## 六、★★ 真机那一轮（2026-10-11 晚上，用户给的视频）

前面所有数字都来自 `p1.mp4` / `p4.mp4`（我自己找的样本）。
这一节是**用户真的给了一个视频、游戏也开着**的那一轮 ——
它推翻了本文档前面两处说法，值得单独记。

**视频**：`liangyuan.f100024.mp4`（B 站「在下油甘 3.5 无主的梁鸢 60 个全收集」）
**规格**：1280x720、30fps、**61156 帧 = 34.0 分钟**

### 6.1 ⚠ 建库耗时被严重低估（差 20 倍）

```
只算描述子（learn_keys=None）     73 秒      ← 前面那张表的数
描述子 + 真 OCR 学按键          1529 秒 = 25.5 分钟   ← ★ 工具页走这条
```

差的就是 OCR：**4078 帧 × 0.359 秒/帧 ≈ 1462 秒**。
所以建库的真实耗时 ≈ **视频时长 × 0.75**，与视频长度成正比。

> ⚠ 我一度在 README 写「27 分钟的视频约 1~2 分钟」——
> 那是**只建描述子**的旧数。工具页 `learn_keys` 默认 `True`，
> 照 1~2 分钟等会以为程序挂了。已改。
>
> 工具页那条状态栏显示的是 `正在建库… xx%（n/总数 帧）`，
> **没有 ETA**（别照 `build_liangyuan.py` 的输出去找界面上的 ETA ——
> 那是诊断脚本自己打的，不是工具页）。

### 6.2 ★★ 「学到 0 个按键」是我的判据太窄，不是视频没提示

第一次建库（含 OCR）结果：

```
参考帧 4078 · 覆盖 34.0 分钟 · 大小 28.5 MB · 耗时 1529 秒
解析不出 111 帧 · ★ 学到按键 0 次
```

当时判断是"这视频是骑摩托赶路型，没有交互提示"。
**错了。** 把提示区得分最高的帧裁出来看，清清楚楚是：

```
[F] 鸱吻          ← OCR 也读对了（'F 鸱吻'）
```

是我的解析判据要求「必须含动作词」，而「鸱吻」是机关名 → 全被丢掉。

修法是**按形状判**（开头是交互键 + 后面还有内容），
但必须有「开头那个键得在 `INTERACTION_KEYS` 里」这道闸 ——
否则 `'A B C'` / `'B 方案'` 这类场景杂字会被当成按键，
而 **A / D 是转视角键**，误按会让机器乱转。

修完重扫（只重扫按键，不重建描述子矩阵）：

```
扫 4078 帧 → 读到文字 111 帧（68 帧解析不出键）
           → 13 条提示 → 合并成 10 次按键（MAX_CONSECUTIVE=6）
```

```
   2.0s  F「F 鸱吻」          51.5s  F「F 前往今州」
1258.5s  F「F 朴素奇藏箱」     1357.0s F「F 鸟蛋」
1998.0s  F「F 破坏机傀」
```

那 68 帧解析不出的，抽查都是**别的东西**（`小型信标记录着范围内的野外数据…`
是说明文字、`倚枝岭` 是地名、`9.96`/`450` 是数字）——
解析层正确地拒绝了它们：**宁可少按，不可乱按**。

### 6.3 ★ 真机抓到一个会「静默抓错窗口」的 bug

用户一边开游戏、一边在浏览器看攻略视频时：

```
含关键字的窗口 2 个：
  Chrome_WidgetWin_1  1536x816   ← 浏览器（标题里有「鸣潮」）
  UnrealWindow        1536x864   ← 游戏
```

`GameWindow.find()` 原来只按**标题**匹配、取**面积最大**的。
那次游戏恰好多 2 像素高才选中游戏 —— **是运气不是正确**。
一旦抓错：截图全拍浏览器、按键也发给浏览器，而**界面一切正常**。

修法：认 **窗口类名** `UnrealWindow`（鸣潮是 UE 游戏，类名是引擎建的、
改不了），类名命中优先，都没有才退回标题。
回归测试 `tests/test_game_window_pick.py`。

### 6.4 ⚠ 这一轮**没有**验证到的东西

* **真机试跑**（标定 `PX_PER_TURN_SEC` + 实际走一段）—— 没做，
  建库耗掉 25 分钟后这轮就结束了
* **OCR 的实际产出率**在这个视频上是 111/4078 = **2.7%**
  （`p4.mp4` 那次是 23.4%）—— 提示条密度**因视频而异**，
  不能拿一个视频的比例去推另一个

## 八、参考库的存放（**一个视频一份**）

```
<用户数据>/explore_gap/
    ├── 无光之森找宝箱_a1b2c3.npz     ← 视频 A 的库
    ├── 无光之森找宝箱_a1b2c3.src      ← 源视频路径（列表用，不解压 npz）
    ├── 无光之森找宝箱_a1b2c3.meta     ← 帧数/时长（列表用）
    └── 七丘声匣_d4e5f6.npz           ← 视频 B 的库
```

* 库名 = ``sanitize_stem(视频名)`` + ``_`` + **源路径**的短哈希
  （中文原样保留；哈希保证"同名不同视频不撞"+"同一视频不攒副本"）
* ⚠ **源视频不能删 / 改名 / 移动** —— 库只存描述子，对齐要回源视频取帧。
  列表会把「源视频不在了」标出来（那时 `runnable=False`）
* 工具页的「移除」只删库和两个 sidecar，**绝不动源视频**
* 能跑的库多于一个时**不自动挑** —— 要求用户在任务配置里指定
  （跑错路线会乱走，比"没跑"糟得多）

### ⚠ 这里修过一个真 bug

最初库是**一个固定文件名**（`video_follow_ref.npz`），于是
**上传第二个视频会把第一个的库覆盖掉**。

而用户要的是「我上传一个视频，你能跟着视频做」——
一个视频 = 一条路线 = 一份库，所以必须能共存。
现在由 `core/explore_gap/catalog.py` 管命名与列表。

### ⚠ 上传的两条路必须给同一个字符串

拖放走 Qt 的 ``url.toLocalFile()``，在 Windows 上返回**正斜杠**
（``C:/Users/...``）；文件选择框给的是**反斜杠**。

两条路不统一的话，同一个文件会算出**两份库**（因为库名里的哈希
是按路径算的）。所以拖放那条路统一走 ``os.path.normpath``。
这个是测试抓到的。
