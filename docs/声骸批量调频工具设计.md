## 0. 实现后补记：又抓到一个原版 bug

设计阶段漏了、写代码时才发现的**第三处必须改**：

原版的属性名比较是**子串匹配**：

```python
if target_main in current_main[0].name:      # 原版
```

而 `"攻击" in "攻击百分比"` 是 **True**、`"暴击" in "暴击伤害"` 也是 **True** ——
于是「目标 攻击 / 当前 攻击百分比」会被**误判成"已经相同"并抛异常**，
而它明明是该改的。**这是比"已经相同"本身更常见的中断原因。**

→ 实现里换成归一化后的**精确相等**（`stat_matches()`），
并把 OCR 噪声（前缀 `+`、空白、`主属性` 字样、全角 `％`）一起吃掉。
回归用例含**反证**（`test_original_substring_bug_is_real`）。

**另外**：设计里说"已经是目标属性 → 跳过并继续"，实现时发现**"继续"做不到** ——
ok-ww 的循环永远处理列表里**第一个**声骸，跳过它之后下一轮还是它（过滤器没变），
会**死循环**。所以改成：**记一次「跳过」→ 停下 → 给出可操作说明**
（"把过滤条件收紧、排除目标属性后重跑"）。这比死循环或静默卡住都强。

## 0b. 实现后又收到两处修正（2026-09-26 当天）

**① 选项表里三个名字是错的**（用户指出）：
原版写 ``攻击`` / ``生命`` / ``防御`` —— 那是**副词条**形态。
声骸**主属性**只有百分比形态，拿 ``攻击`` 当目标在游戏里根本选不到。
→ 改成 ``攻击百分比`` / ``生命百分比`` / ``防御百分比``（默认值是 ``攻击百分比``）。

顺带查到 ok-ww 自己的 ``FiveToOneTask`` 用的是**带「力」**的写法
（``main_stats = ["攻击力百分比", …]``、``black_list = ["主属性攻击力", …]``），
说明游戏 UI 里可能是「攻击**力**百分比」。所以实现**不靠字面量硬对**：
比较走归一化（吃掉「力/值」），选项检索把「力/值」做成可选 —— 两种写法都能命中。

**② 我第一版的选项检索又犯了一次子串匹配的错**（被测试抓出来）：
写的是 ``re.search(target, …)``，于是 ``暴击`` 会先撞上面板里的 ``暴击伤害`` 那个框 →
**把主属性改成用户没要的那个**，而且界面看起来"成功了"。
→ 匹配式两头加锚点（只允许前缀 ``主属性/主音属性``、空白、``+``），
并把这条钉成用例 ``test_crit_pattern_does_not_hit_crit_dmg``。
**同一个坑在同一个文件里犯了两次** —— 可见"属性名必须整串比对"这条得一直留着。



## 1. 它是什么

游戏里的「**调频**」＝ 花材料**改声骸的主属性**（主音属性），走声骸详情页的「**数据重构**」。

ok-ww 的对应任务是 `ChangeEchoTask`，自述是
`🎛️ 批量修改声骸主属性(仅支持简中游戏语言)`。
MyTools 要的就是它 —— 同样的流程，但**判定/容错按 MyTools 的标准来**。

**和「声骸自动强化」的区别**（别混）：

| | 声骸自动强化 | 声骸批量调频（本工具） |
|---|---|---|
| 改的是 | **副词条**（强化并调谐） | **主属性**（数据重构） |
| 目标 | 按双爆/有效词条判定，保留或弃置 | 把一个属性统一改成另一个 |
| 消耗 | 强化经验材料 | 调频材料 |

## 2. 功能范围

### ✅ 做什么

1. **批量把一批声骸的主属性改成同一个目标属性**。
2. 目标属性 12 选 1：

   `攻击百分比` `暴击` `暴击伤害` `生命百分比` `防御百分比` `共鸣效率`
   `冷凝伤害加成` `热熔伤害加成` `导电伤害加成` `气动伤害加成` `衍射伤害加成` `湮灭伤害加成`

   > ⚠ **修正过 ok-ww 原版的选项表**：原版写的是 ``攻击`` / ``生命`` / ``防御``，
   > 但那是**副词条**形态 —— 声骸**主属性**只有百分比形态，
   > 拿 ``攻击`` 当主属性目标在游戏里根本选不到。
   >
   > 另：ok-ww 自己的 `FiveToOneTask` 用的是**带「力」**的写法
   > （`main_stats = ["攻击力百分比", ...]`、`black_list = ["主属性攻击力", ...]`），
   > 说明游戏 UI 里可能是「攻击**力**百分比」。
   > 所以实现里**不靠字面量硬对**：比较走归一化（吃掉「力/值」），
   > 选项检索的匹配式把「力/值」做成可选，两种写法都能命中。

3. **逐个体处理**：点进详情 → 读当前主属性 → 选目标属性 → 数据重构 → 领回 → 下一个。
4. **结束时给出报告**：成功几个 / 跳过几个 / 失败几个（以及失败原因分布）。

### ⚠️ 范围边界（明确不做）

| 不做 | 原因 |
|---|---|
| **不改副词条** | 那是「强化并调谐」，归声骸自动强化工具 |
| **不筛选声骸** | 筛选交给**游戏内的过滤器**（用户自己设），工具只处理"过滤器给出的那批" |
| **不判断数值高低** | 只换主属性的**种类**，不管换出来的数值是多少 |
| **不做"值不值得换"的决策** | 那是用户的事；工具不做价值判断 |
| **不支持非简中游戏** | ok-ww 原版就只支持 `zh_CN`：属性名 / 按钮文案都是中文字面量做 OCR |

### 输入 / 输出

- **输入**：用户选的「目标属性」+ 游戏里当前停着的位置
- **前置条件**（写进工具页，跟强化工具一致）：
  1. **以管理员运行**（否则点击发不进游戏，见总目录「权限是硬门槛」）
  2. 游戏**窗口模式**（无边框最稳）
  3. 自己走到：**背包(B) → 声骸 → 用过滤器筛出要调频的 → 按等级升序排序**，停在这个列表界面
- **输出**：界面报告 + `data/okww/logs/` 日志 + 每个成功声骸的截图

## 4. 关键实现要点

### 4.1 流程（ok-ww 原文，`ChangeEchoTask.run()`）

```
while True:
    找「培养」按钮 ── 没有 → raise「必须在背包声骸界面过滤后开始!」
    找「声骸技能」（详情面板特征）── 没有 → 任务正常结束，return
    连点「培养」直到它消失（≈5s 上限）          # 进详情页
    等「声骸强化」出现
    读**当前主属性**  ← 区域 (0.09, 0.20, 0.15, 0.26)
    ── 已等于目标 → raise「目标属性和当前属性相同…」
    点 (0.04, 0.41)   + 等「主音属性」           # 切到主音属性页
    点 (0.52, 0.71)   + 选目标属性               # 打开属性选择
    点「确认」
    点「数据重构」（区域 0.37,0.82,0.64,0.99）
    等「获得声骸」
    esc() 回列表
    成功数 +1
```

### 4.2 ⚠️ 必须改掉的四处（照抄会重蹈覆辙）

**① 语言门禁 —— 不改任务会"凭空消失"**

```python
self.supported_languages = ["zh_CN"]
```

ok-script 的 `init_tasks()` 拿 `app.locale` 比对，**不满足就静默不注册**。
宿主无 GUI → `app.locale` 是 `en_US` → 任务进不了引擎，点「运行」只得到「找不到任务」。
**这正是「声骸自动强化」踩过的头号坑**（2026-09-24）。

→ **必须 `self.supported_languages = []`**，并在 `run()` 里自己做一道语言检查 + 告警。

**②「目标属性相同」是 `raise` —— 会让整个任务死掉**

```python
if target_main in current_main[0].name:
    raise Exception('目标属性和当前属性相同, 请修改声骸过滤条件!')
```

过滤器筛出来的一般是"同一套装 / 同一位置"的一批声骸，里面**必然混着几个已经是目标属性的**。
一旦碰到，原版**整个任务中断** —— 而用户要的是"把这批都改成目标属性"，
已经是的**跳过就好**。

→ 改成**跳过并继续**，计入「跳过」计数。
（这就是「跑到一半自动停止」的同一类病：把可恢复状态当致命错误。）

**③ `raise_if_not_found=True` 的每一处都是致命中断**

`'声骸强化'` / `'主音属性'` / 目标属性 / `'数据重构'` / `'获得声骸'` 五处。
UI 过渡期间 OCR 抓空一个就可能炸整局。

→ MyTools 侧对每一步做**有限重试**（如 3 次 × 1s），仍失败则：
**`esc()` 回列表 → 把这个声骸计入「失败」→ 继续下一个**，
而不是退出任务。连续失败 N 个（建议 3）才整体停下并明确报告。

**④ `esc()` 的循环条件要复核**

```python
def esc(self):
    while not self.find_echo_enhance() and time.time() - start < 5:
        self.send_key('esc', after_sleep=1)
```

`find_echo_enhance()` 找的是「培养」＝**已经在列表页**。逻辑没错，
但**上限 5 秒 / 每次 sleep 1 秒**在详情页较深时可能不够 → 回到列表失败 →
下一轮找不到「培养」→ 又 raise。

→ 把上限放宽到 10 秒，并**在回来后断言「培养」确实在**，
不在就再补一次 `esc`（而不是让下一轮去炸）。

### 4.3 复用现有的东西（不要重写）

| 要用的 | 从哪来 |
|---|---|
| 引擎宿主 / 启停 / 日志 / 报告快照 | `auto_combat/okww_boot.py`（**加一条 `TASKS` 映射即可**） |

## 7. 风险

1. **坐标是硬编码的相对值**（`(0.04,0.41)` / `(0.52,0.71)` / `(0.37,0.82,0.64,0.99)`）。
   游戏 UI 一改版就全部失效 —— 这是这类工具的天生代价，不是本工具特有的。
2. **主属性选择面板的选项顺序**靠 OCR 匹配属性名定位，不依赖顺序 ✔，但仍然怕改版。
3. **调频材料会被真的消耗掉**。第一次跑建议**只筛 2~3 个**声骸试。
4. **上游同步**：`ChangeEchoTask` 我们只做增量覆盖，`run()` 主体仍来自 ok-ww。
   上游改流程时要做一次 diff（判定哪些覆盖还能挂住）。
   → 记进 `docs/阶段性总结.md` 的待办。
