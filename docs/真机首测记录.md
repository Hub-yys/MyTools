## 一、★ 真 bug：描述子相似度**不减均值**（已修）

**文件**：`src/core/explore_gap/descriptor.py`

### 现象

游戏窗口抓图正常，但定位失败。真机帧查全库：

```
最高 0.9096   中位 0.8093   均值 0.8036      ← 分布是平的
```

"最像"的一帧是视频 **20.4 分钟**处的一张**地图界面** ——
与用户所在的广场画面**毫无关系**。
对照：视频自己的第 0 帧查库 → `index=0`、相似度 `1.0000`（链路没坏）。

### 根因

```python
v = np.where(MASK, gray, 0.0).ravel()   # 灰度 0~255，全非负
return v / np.linalg.norm(v)            # 只做 L2 归一化
```

L2 归一化只消**乘性**亮度差，**消不掉加性直流分量**。
自然画面灰度均值很大（库内中位 82.4、真机帧 103.4），
于是所有向量都偏向"全 1 方向" → **相似度被整体亮度主导**。

决定性合成实验：

| 实验 | 原版 | 减均值后 |
|---|---|---|
| 竖条纹 vs 横条纹（内容正交） | 0.5024 | **0.0000** |
| 纯灰 100 vs 纯灰 200（无内容） | **1.0000** | — |

**纯色对比满分** —— 度量根本没在量"内容"。
真实库内"相距 >500 帧（无关）"中位 **0.8269** vs "相距 1 帧" 0.9489，
**只差 0.12**。

### 为什么之前没发现

离线验收是**开卷考试**：视频自己的帧查自己的库，两边亮度色调完全一致，
直流分量是同一个值 —— **它反而帮忙了**，所以命中率一直显示 94.8%。

### 修法（已落地）

```python
inside = gray[MASK]
centered = inside - float(inside.mean())   # ★ 减均值：只留明暗结构
v = np.zeros(DH * DW, dtype=np.float32)
v[MASK.ravel()] = centered                 # 遮罩外保持 0
return v / norm if norm > 1e-6 else None
```

⚠ **均值只在遮罩内求、也只在遮罩内减** —— 对整个向量求均值会被
遮罩外那 41% 的 0 稀释，减完在遮罩外留下非零常数。

### 实测效果（回视频重抽 4078 帧原始灰度对比）

| 度量 | 最高 | 中位 | 跨度 | margin(1-2) |
|---|---|---|---|---|
| 原版 | 0.9096 | 0.8093 | 0.1002 | 0.0003 |
| **减均值后** | 0.5183 | 0.0815 | **0.4368** | 0.0035 |

跨度 **4.4 倍**。

## 二、阈值重标（度量变了，旧阈值作废）

### `MARGIN_MIN`（窗口内定位）

用 4078 帧、各约 400 样本重标：

```
「对」余量：中位 0.4434   25% 0.3396    5% 0.0013
「错」余量：中位 -0.6895  95% -0.4789   最大 -0.0001   ← 全是负的
```

**两组几乎不重叠**。扫描：

| 阈值 | 漏（对被打掉） | 错（错被放过） |
|---|---|---|
| 0.000 | 0.0% | 0.0% |
| **0.020** | **7.3%** | **0.0%** |
| 0.100 | 7.3% | 0.0% |

取 **0.02**：错 0%、漏 7.3%。符合项目"宁可漏，不可错"的取舍。

### 阈值重标结果

**`MARGIN_MIN`（窗口内定位）**：0.01 → **0.02**

用 4078 帧、各约 400 样本重标：

```
「对」余量：中位 0.4434   25% 0.3396    5% 0.0013
「错」余量：中位 -0.6895  95% -0.4789   最大 -0.0001   ← 全是负的
```

**两组几乎不重叠**。取 0.02：错 0%、漏 7.3%。

**`ALIGNED_MARGIN_MIN`（对齐后打分）**：0.02 → **0.15**

```
「对」余量：中位 0.4596  25% 0.3217   5% 0.1908
「错」余量：中位 0.0678  95% 0.2505   max 0.3628
```

| 阈值 | 漏 | 错 |
|---|---|---|
| 0.02（旧值） | 0.0% | **80.0%** |
| 0.10 | 3.3% | 26.7% |
| **0.15** | **3.3%** | **10.0%** |
| 0.20 | 10.0% | 6.7% |

### ⚠ 一个必须记住的局限

余量 = "最佳 减 第二名"，而第二名是从**同一个窗口**里选的。
**窗口整体落在错的地方时，5 个候选全错，余量照样能拉开**
（实测"错"组 max 0.3628 就是这么来的）。

→ **余量管"几个候选里认没认准"，管不了"这些候选是不是都在错的地方"。**

后者应该由**绝对分数**负责 —— 实测分得很干净：

```
「对」的绝对分：0.9999 量级
「错」的绝对分：0.12 ~ 0.39
```

⚠ 给对齐路径加一道**绝对分数门槛**是待定的设计改动，
要先跟用户确认再动（它会改变"什么时候停下来报错"的行为）。

## 三、★★ 第二个真 bug：**分辨率不同 → 相位相关永远失败**（已修）

### 现象

真机帧走对齐路径（``locate_aligned``），**连门槛放到最低都返回 ``None``**
—— 意味着没有一个候选活下来。而视频自己的帧走同一条路是完美的
``0.9999``（说明实现是对的）。

### 根因

``world_region()`` 原来**按比例裁原图** → 裁出来的尺寸**跟着分辨率变**：

```
视频 1280x720   → (510, 1180)
真机 1536x864   → (612, 1416)     ← 形状不同！
1080p           → (765, 1770)
```

而 ``Locator.phase_shift()`` 第一句就是：

```python
if a.shape != b.shape:
    return None
```

→ **只要游戏分辨率和视频分辨率不一样，相位相关每次必返回 None**，
所有候选被跳过 → **定位必定失败**。

⚠ 这跟"人在不在路线上"**完全无关** —— 就算人站在一模一样的位置、
朝向也一样，只要分辨率不同就必然失败。
（用户的游戏是 1536x864，视频是 1280x720。）

### 修法

`world_region()` 先把裁剪区**缩放到固定规范尺寸** `PHASE_CANON=(1180,510)`，
两边形状永远一致。宽高比一致（1180/510 ≈ 2.314）所以缩放不引入形变。

新增 `phase_scale(frame)` / `crop_box(frame)`：因为相位相关在**规范尺寸**上
量位移，必须换算回**当前帧自己的**像素 —— 否则执行器的
`PX_PER_TURN_SEC`（真机分辨率下标定的）会整体偏掉。
`phase_shift` 现在返回的是**当前帧像素**。

### 验证

```
修前：phase_shift(参考帧, 真机帧) = None
修后：phase_shift(参考帧, 真机帧) = (289.6, -20.1, peak=-0.0018)
      ✓ 形状一致 (510,1180) == (510,1180)
```

## 五、★ 方案层面：这个视频**不是一条能让机器走的连续轨迹**


### 视频结构

**27 处稳定剪切**，切成 **28 段**。段长中位 51.5 秒，最长 268 秒。
剪切判据（避免把骑车时的快速变化误判）：

```
consec[i-1] 高   旧场景稳
consec[i]   低   ← 跳了
consec[i+1] 高   新场景也稳
```

剪切对照图显示：每次剪切都是**从"刚收集完的地方"跳到"下一个传送点/室内"**。

### 视频里出现过的移动方式

骑摩托（大量）、飞行/滑翔、跑图、爬山、游泳、进洞、战斗。

### 按键表只有 10 次 F

`F 鸱吻` / `F 前往今州` / 6×`F 朴素奇藏箱` / `F 鸟蛋` / `F 破坏机傀`
—— **一次空格都没有**。

原因是**结构性的**：飞行/滑翔是直接按空格，**屏幕上不显示提示**，
没有提示 OCR 就没东西可读。

### 结论

标题「3.5 无主的梁鸢 60 个全收集」= **覆盖 60 个收集点的攻略路线**，
不是"从 A 走到 B"。它是给**人**看的：人看它知道去哪，然后自己跑、自己传送。

## 六、★★ 第三个真问题：定位 **23 秒/帧**，闭环根本跑不起来（已修）

### 现象

真机连拍 10 帧做连续定位，每帧耗时 **11~23 秒**：

```
#00 → idx=1690 (22632ms)
#01 → idx=1697 (17374ms)
...
```

### 根因

``locate_aligned`` 对 top_k(=5) 个候选**各取一次原图**做相位相关，
而 ``library.frame_image()`` 是**回源视频 seek**：

```
实测（232MB 的 mp4）:
  顺序读 300 帧        11.7 ms/帧
  seek + read 一次     **3087 ms**   ← 慢 264 倍
```

5 个候选 × 3 秒 ≈ 15 秒，加上相位相关，正好对上观测到的 23 秒。

### 为什么这是硬约束

闭环要 **~10 次/秒（100ms/帧）** 才能跟住走路。
23 秒/帧 = **慢 230 倍** —— 这不是"优化"，是"能不能用"。

### 修法：给取原图加 LRU 缓存

实际运行时**候选高度重复**（每帧都在同一小段窗口里搜），
所以缓存命中率很高。

⚠ 不能全缓存：34 分钟视频有 4078 帧 × 2.7MB ≈ **11GB**。
所以用 LRU 淘汰，容量 ``DEFAULT_FRAME_CACHE = 64``（≈173MB）。

### 效果

```
修前：23487 ms
修后：  528 ms      ← 44 倍
（第一次调用仍慢 —— 冷缓存，之后命中内存）
```

⚠ 528ms 仍**高于** 100ms 的目标 —— 而执行器里 ``FRAME_INTERVAL = 0.1``
正说明设计目标是 **10 次/秒**。所以这条**还没修完**。

要继续提速的方向（本轮不做，等定位可靠了才有意义）：

* 候选数 ``TOP_K`` 从 5 降下来（先粗筛再精评）
* 相位相关跑在更小的分辨率上
* **预取**相邻参考帧（位置连续 → 下一帧的候选可以提前取）
* 把"取原图"整个换掉 —— 库重建时**顺便存一份缩略图**，
  相位相关用缩略图就够（现在每次都要回源视频 seek）

### 新增测试

`tests/test_explore_gap_cache.py`（13 条）：LRU 淘汰顺序、命中刷新、
不同帧号不串味、close 清缓存、容量合理。

## 七、★★ 抓图 vs 按键：**能后台看，不能后台按**

### 现象

真机第一次抓图抓到的是 **DSH 自己的窗口**。
原因：诊断脚本用 `GameWindow.grab()`，那是 **mss 屏幕区域截图**
（GDI `BitBlt`），抓的是**屏幕那块矩形** —— 屏幕上盖着什么就抓到什么。

### 一度以为无解

* `PrintWindow`（带/不带 `PW_RENDERFULLCONTENT`）→ **全黑**
  （本轮实测确认：`非黑像素 0.0%`，项目里那条旧结论成立）
* 连续采样 150 秒想"等游戏在前台的瞬间" → **一张都没抓到**
  （用户要看报告，DSH 就一直盖着 —— 这是**结构性死锁**，不是偶发）

### ★ 真正的解法：WGC（Windows Graphics Capture）

`windows-capture` 这个库走的是系统级窗口捕获，DWM 直接把**窗口自己的**
合成内容交出来，**和窗口是否被遮挡无关**。

实测（**脚本自己把 DSH 提到最前**，制造确定的遮挡状态）：

```
已把 DSH 提到前台
当前状态：游戏是前台=False   被谁盖住=['Chrome_WidgetWin_1']
WGC 抓图：✓ (1119, 1922, 3)  均值 109.2  全黑 0.0%
         → 抓到的**是游戏画面**（广场 + 秋鸿 NPC），不是 DSH
对照 mss：均值 50.9（抓的是 DSH）
```

### ★★ 抓图 vs 按键 —— 两者的后台能力**完全不同**

这是最关键的一点，**必须分开看**：

| 能力 | 被遮挡 | 最小化 | 结论 |
|---|---|---|---|
| **抓图**（WGC） | ✅ 能 | ⚠ 没验成 | **后台可抓** |
| **按键**（win32 事件） | — | — | ⚠ **被静默丢弃**（实测） |

#### ⚠⚠ 按键这条是真瓶颈：**本进程比游戏低一级**

    "keybd_event 更是**静默丢弃**"

**→ 结论：**

| 要做的事 | 能不能后台 | 卡在哪 |

| **看**（抓图） | ✅ 能 | 已解决（WGC） |
| **按**（发输入） | ❌ 不能 | **权限**（Medium < High） |

## 八、★★★ 找到根因：描述子认「机位」，不认「地点」

这一节解释**为什么"人在同一个地方却匹配不上"**，并给出**能走通的条件**。

### 9.1 先确认：视频里**确实有**用户那个广场

视频 **3.1 秒**那一帧（`_probe/chiyi.py` 抽出）：

* 大树 / 长椅 / 满地粉花瓣 / 同样的几何建筑
* 屏幕上写着 **「鸱吻 / 声匣回收」**

用户画面：

* 同样的树、长椅、粉花瓣、几何地砖
* 屏幕上写着 **「秋鸿 / 梁鸢回收」**

视频前言原文（OCR 逐字读出的）：

```
★ 将这些消息交予【秋鸿或鸱吻】，他们会依此了解玄方城的过去…
```

→ **两个 NPC 在同一种交付广场上。**
所以用户一开始说的「**地方一致，但 NPC 不一致**」**完全成立** ——
不是我中途猜的"区域不对"。

> ⚠ 我这一轮还犯过一个错：把任务名「煙云幽远心剑鸣」**误读成区域名**
> 「烟云幽径」，并据此下了"用户区域不在视频里"的结论。
> **放大复核**后发现那是任务名，结论作废。
> 教训：OCR 结果要**放大肉眼复核**再用它下结论。

### 9.2 ★★ 那为什么分数只有 0.20？—— 机位容差

实测（`_probe/view_tolerance.py`，全部走生产 `descriptor`）：

| 对比 | 相似度 |
|---|---|
| 同机位（±0.6 秒内） | **0.96 ~ 1.00** |
| 镜头一动（+0.9 秒） | **-0.06 ~ +0.04**（已经认不出） |
| **同一地点、不同机位**（用户 vs 视频 3.1s） | **+0.2014** |
| 完全无关的随机帧 | 中位 +0.0411，**最高 +0.2449** |
| 开卷基准（同帧查自己） | 0.9999 |

★ **「同一地点、不同机位」的 0.20 落在「完全无关」的分布里**
（随机帧最高都有 0.2449）。

→ **描述子认的是「机位像不像」，不是「地方是不是同一个」。**
 同一个广场，只要镜头朝向 / 远近不同，就被判成"不认识"。

### 9.3 ★★★ 但这不致命：**锁定之后跟踪是准的**

上面那条限制只影响**入场**（从哪一帧开始跟）。而"跟着走"时，
每帧要匹配的是**相邻参考帧**，机位差极小 —— 那正是描述子擅长的区间。

实测（`_probe/locked_mode.py`）：取 40 个位置，每个模拟
「机器和视频差了 k 帧」（k ∈ [-8,+8]，即走快/走慢），
用生产 `locate_windowed` 在 ±30 帧窗口里重定位：

```
查询总数   : 40
命中（±2帧）: 40  (100.0%)
定位到但错  : 0   (0.0%)
完全没结果  : 0   (0.0%)
误差：中位 0 帧   最大 1 帧   （1 参考帧 = 0.50 秒）
相似度：0.9995 ~ 0.9999
```

**100% 命中、误差 0 帧。** 所以"跟"这个动作本身**成立**。

#### 再用**生产 `Locator.measure()`** 复验（含全部门槛）

上面那个 100% 用的是底层 `locate_windowed`。生产跑的是
`Locator.measure()`，它**多两道闸**：相位相关 `PEAK_MIN`、
以及本轮重标的 `ALIGNED_MARGIN_MIN=0.15`。
**门槛会不会把正确的匹配也挡掉？** 必须验。

实测（`_probe/track_prod.py` / `track_safety.py`，模拟"已锁定后连续跟 30 步"，
每步夹带 ±2 帧抖动）：

```
步     真值     查询     定位    误差      sim    peak  trusted
  1   1202   1203   1203    +0   0.9999  1.0000     True
  2   1204   1204   1204    +0   0.9998  1.0000     True
 ...（每步误差都是 +0，sim 0.998~0.9999，peak 1.0000）
 29   1245   1245   1245    +0   0.9997  1.0000     True
```

★ **按安全性三分类**（这个分法比"命中率"更重要）：

```
① 定位正确（±2 帧）  :  28  (93%)
② 主动拒绝（None）   :   2  ( 7%)   ← 安全：执行器 WAIT，不产生动作
③ ★ 定位到错的地方   :   0  ( 0%)   ← 危险：会朝错方向走
```

→ **危险的那一类是 0** —— 正是项目要的「宁可漏，不可错」。
  凡是给出结果的，**误差全是 0 帧**；给不出的就老实拒绝。

> ⚠ 我第一次统计时把「`None`」和「定位到错的」**混为一谈**，
> 打出"有定位错误"。**那个说法不准确** ——
> 两者的安全性完全不同，必须分开算。已改。

### 9.4 结论：瓶颈是**入场**，不是「跟」

| | 可行性 | 依据 |
|---|---|---|
| **从视频起点开始一步一步跟** | ✅ **已验证**（离线 40/40） | 9.3 |
| **从中途任意位置插进去** | ❌ **做不到** | 9.2（机位容差太窄） |

→ 要走通，需要满足**其中一个**：

1. **从视频起点开始** —— 人先站到视频开头那个机位，然后启动
2. **站到某一个视频帧的机位** —— 对着视频画面调好，然后启动
3. **换更鲁棒的描述子**（对视角不变）—— 大改：
   牵动建库格式、全部阈值、全部实测数字

#### ★ 入场容差实测：**是人做得到的**（我中途写错过，这里改正）

9.2 那条"机位容差窄"容易让人以为"人要调得极准"。**实测不是那样**
（`_probe/entry_test.py`：拿视频 3.1s 做扰动，阈值 0.30 =
随机无关帧的上限 0.2449）：

| 扰动 | 容忍到 | 相似度 |
|---|---|---|
| **平移**（站位左右差） | **≤ 5%**（1280 宽 ≈ 64px） | 0.40 |
| **旋转**（朝向差） | **≤ 10°** | 0.41 |
| **缩放**（远近差） | **≤ 1.35x** | 0.39 |

**10° / 5% / 1.35x 是人对得上的** —— 对着视频画面转一下就行。

> ⚠⚠ **第十节的重要更正**：这组数字来自**视频 3.1s（贴脸近景）**，
> 是**最不利**的一档。同一轮换到开阔场景（视频 10 分钟）重测，
> 同样 5% 平移 → **0.79**（而不是 0.40）。
> 全片 11 个时刻实测 **0.325 ~ 0.792，差 2.4 倍**。
>
> **→ 容差不是常数，它取决于画面内容。** 上面这组数应读作
> **"最坏情况"**。至于"取决于什么"——**猜了两个原因都被否掉**，
> 详见第十节。

#### ⚠ 但用户当前的偏差**远超**这个容差

分解用户画面 vs 视频 3.1s（`_probe/entry_calib.py`）：

```
相位相关: dx=+2.4 dy=+175.6 peak=-0.0130
          ★ peak≈0 → **连平移都量不出来**，
            说明差异不是"偏了一点"，而是**取景完全不同**
最终相似度 = +0.2014
```

视频 3.1s 是**贴着鸱吻近看**，用户是**俯视广场地砖** ——
取景范围差得远（不是 1.35x 那种轻微缩放）。

→ 所以：容差**够用**，但人**得先站到机位上**。
  B 方案（对着视频调机位再启动）**是可行的**。

**建议先做 1 或 2**（成本最低，且能立刻用 9.3 的结论验通）。

### 9.5 ⚠ 还有一件事没验：真机上的"同机位"差多大

9.3 的 100% 是**离线**（视频自己的帧 + 人为偏移）。
真机还多一层差异：**同一机位下，游戏画面 vs 视频画面**
（显示器 / 录制 / HUD 差异）。

这个差异有多大**还没量**。方法：让用户站到视频某一帧的**准确机位**，
抓一帧和那一帧比 —— 如果也在 0.99 附近，9.3 的结论可以直接移植真机。

## 九、WGC 用法的三个坑（会重复踩，记下来）

用 `windows-capture` 抓游戏画面时踩到两个**工具链**层面的坑
（不是业务逻辑）。它们共同的特点是：**报错信息不明显，或者被静默吞掉**。

### 坑 ①：`frame.frame_buffer` **不是 C 连续**（⚠ 机制没查清，但对策确定）

**确定的部分 —— 对策**：

```python
# ✓ 先 copy() 拿到独立、连续的缓冲
arr = np.asarray(frame.frame_buffer).copy()
bgr = cv2.cvtColor(arr, cv2.COLOR_BGRA2BGR)
```

★ **而且必须「在回调里就拷」** —— 回调返回后那块缓冲会被复用。
不拷的话，事后读到的可能是**完全别的画面**，而且**不报错**。
这条是**能确定性验证**的（见 `tests/test_explore_gap_capture.py`
的 `test_result_is_independent_copy`），也是真正伤人的那条。

**⚠ 没查清的部分 —— 诚实标注**：

第一版我写的是 `np.frombuffer(buf, ...).reshape(h, w, 4)`，
真机上抛过 `ValueError: ndarray is not C-contiguous`。

但**我后来没能复现它**：试了列切片 / 行切片 / 转置 / F-order /
`as_strided` 五种构造，**`cvtColor` 和 `reshape` 全都能接受**
（`_probe/noncontig.py` 实测全部返回 OK）。

所以那个错的确切触发条件**还不知道** ——
可能是 `frame.width/height` 与 buffer 实际元素数不匹配，也可能是别的。
**需要真窗口才能探测**（脚本已备好：`_probe/buf_probe.py`，
要游戏开着才跑得了）。

→ 所以这条**不是"已查明的库缺陷"**，而是
「**踩到过、对策确定、根因待查**」。写在这里是为了下次别再绕。

**这个坑为什么难查**：如果回调里写了 `except Exception: pass`
（我第一版就是），异常被吞掉，表现只是**"一帧都抓不到"** ——
看起来像"窗口不对/没开游戏"。

→ 现在 `tests/check_explore_gap_game.py` 的 `grab_frames()` 会

### 坑 ②：`windows_capture` 按**窗口标题**找窗口

`WindowsCapture(window_name=...)` 用的是**标题字符串**，
**不是 hwnd**。所以：

* 标题为空的窗口（比如 DSH 自己 `Chrome_WidgetWin_1` 标题是 `''`）
  **根本没法用它抓** —— 实测报
  `Failed to find window: Failed to find a window with the name: x`
* 游戏窗口标题是 **「鸣潮」**，所以游戏**可以**抓（这是关键）

### 坑 ③（附带）：有些系统窗口会让 `start()` **挂住**

实测把捕获目标选成 `Windows 输入体验`（`Windows.UI.Core.CoreWindow`）
或 `Program Manager`（`Progman`）时，`cap.start()`
**既不返回也不报错** —— 直接卡死。

→ 所以自检脚本要**排除这些类名**，并在子线程里 `start()` 以便超时兜底。

### 这三条的合并影响

它们解释了为什么"抓图"这件事在真机上折腾了很久：

```
mss 屏幕截图  → 被遮挡就抓到挡它的窗口（用户一看报告就中招）
PrintWindow   → UE 窗口全黑
WGC           → 能抓，但有上面这三个用法坑
```

**结论：真机验证脚本一律走 WGC，并且必须处理这三个坑。**
参考实现：`tests/check_explore_gap_game.py`。

## 十、容差的决定因素 —— **两个猜测都被否掉**（如实记录）

### 10.1 起因：发现容差**不是常数**

第 8 节量入场容差时用的是**视频 3.1s**（交付广场，贴脸近景）。
这一轮换到**第 10 分钟**（开阔跑图）重测，同样是 5% 平移：

```
贴脸近景（3.1s）   → 0.40
开阔场景（10 分钟）→ 0.79
```

**差近 2 倍。** 所以"容差是常数"这个前提**不成立**。
扩到 11 个时刻全片抽测：

```
相似度 范围 0.325 ~ 0.792     （差 2.4 倍）
```

★ **容差确实取决于画面内容** —— 但"取决于什么"还没查明。

### 10.2 猜了两个原因，**两个都错**

| # | 假设 | 相关系数 | 结论 |
|---|---|---|---|
| ① | 结构越多（边缘密度高）越抗扰动 | **-0.326** | ❌ **负相关**，否掉 |
| ② | 越满足"整体平移"模型（peak 高）越抗扰动 | **+0.080** | ❌ 几乎无关，否掉 |

假设① 是"常识直觉"（结构多应该更好对齐），实测**恰好相反**。
假设② 是我为了解释①的失败而提的，**也不成立**。

→ **容差的决定因素目前未知。** 不编。

### 10.3 否掉的方案：多帧序列入场

本来的想法：单帧入场要求机位几乎一致，
那"连着几帧一起判"也许能靠运动模式抗住机位差。

实测（`_probe/seq_entry.py`）：

```
扰动            单帧最佳   序列平均   序列最差
无扰动          1.0000    1.0000    1.0000
平移 5%         0.7923    0.7588    0.7418
平移 10%        0.7186    0.6586    0.5688
旋转 10°        0.6718    0.6495    0.6327
缩放 1.2x       0.8334    0.8059    0.7910
```

**「序列平均」每一行都 ≤「单帧最佳」。**

而且这**不是实现问题，是数学必然**：平均是**降序算子**，
一组数的平均永远 ≤ 其中最大者。所以"几帧一起看"
**永远**不会比"取最好的那一帧"更高 ——
除非引入**帧间关系建模**（光流 / 位移一致性），
那是完全不同的特征，不是把描述子平均一下。

→ **这条路不用再试了。**

### 10.4 对方案的影响

* ❌ **不能**靠"挑一个好帧做入场" —— 不知道哪个帧抗扰动
  （试了两个判据都不成立）
* ✅ 但 **「从视频起点开始」仍然可行** —— 起点是**双方约定的**，
  人不需要"猜机位"，只要站到开头那儿

→ 所以 **方案 A（从起点开始）依然是唯一有依据的路**。
  "挑个好机位从中间插进去"这条**暂时没有依据支撑**。
